# 三种并发模型性能对比报告 — 进程 vs 线程 vs 协程

---

## 前言

本项目是一个**操作系统课程实践项目**，目标是通过同一个任务（爬取 33 所中国高校的官方网站并提取纯文本），用三种不同的并发策略分别实现，从而在实践中对比进程、线程、协程的特性和性能差异。三个爬虫程序共享相同的数据源和工具函数，只有并发模型不同——这是一次**控制变量的对比实验**。

### 推荐阅读顺序

如果你是初学者，建议按以下顺序阅读（每篇都建立在前一篇的基础上）：

1. **[进程爬虫详解](进程爬虫详解.md)** — 从零理解进程，包含基础概念（I/O、内核态等）的解释
2. **[线程爬虫详解](线程爬虫详解.md)** — 在理解进程的基础上，学习线程如何共享内存
3. **[协程爬虫详解](协程爬虫详解.md)** — 在理解线程的基础上，学习协程如何实现更高效的并发
4. **本报告** — 对比总结三者的性能差异和选型建议

如果你已有一定基础，可以直接阅读本报告了解全局，再按需查阅各详解文档。

## 一、先用一个比喻搞懂三者

为了让完全没接触过并发编程的人也能一看就懂，我们用**餐厅接待客人**来比喻三种模型：

### 进程模型 — 开连锁分店

```
客人来了33桌？那就开33家独立的分店！

分店1（独立的门面+厨房+服务员）→ 服务第1桌客人
分店2（独立的门面+厨房+服务员）→ 服务第2桌客人
...
分店33（独立的门面+厨房+服务员）→ 服务第33桌客人

优点：分店之间互不影响，一家着火了其他照常营业
缺点：开分店成本极高，而且本实现中是一家做完才开下一家（串行）
```a

### 线程模型 — 雇33个服务员

```
客人来了33桌？那就雇33个服务员！

         ┌──── 服务员1 → 服务第1桌
一家餐厅 ├──── 服务员2 → 服务第2桌
 共用    ├──── ...
 一个    └──── 服务员33 → 服务第33桌
 厨房

优点：33个服务员同时工作，比一个人快多了
缺点：雇人有成本（每人要发工资=栈空间），人太多互相挤
```

### 协程模型 — 一个超级服务员

```
客人来了33桌？一个服务员就够了（其实是几个人，但远少于33个）！

超级服务员的工作方式：
  给1桌点完菜 → 菜还在做 → 不等了，去给2桌点菜
  给2桌点完菜 → 菜还在做 → 不等了，去给3桌点菜
  1桌的菜好了！ → 赶紧端过去
  ...

同时最多同时点菜20桌（Semaphore限制），其余排队

优点：人力成本极低，一个人能服务上万桌
缺点：工作安排更复杂（需要记住每桌的状态）
```

## 二、核心概念速览

### 2.1 什么是进程、线程、协程？

| | 进程 (Process) | 线程 (Thread) | 协程 (Coroutine/Async) |
|--|---------------|---------------|----------------------|
| **一句话定义** | 操作系统分配资源的单位，有独立内存空间 | 进程内的执行流，共享内存空间 | 用户态的轻量执行单元，在线程之上运行 |
| **通俗比喻** | 独立的公司，有自己的办公室 | 同一公司的多个员工，共享办公室 | 超级高效的员工，等待时切换做其他事 |
| **调度者** | 操作系统内核 | 操作系统内核 | 用户态运行时（如 Tokio） |
| **内存空间** | 完全独立 | 共享堆，独立栈 | 共享堆，极小的状态存储 |
| **Rust 中创建** | `Command::new()` | `thread::spawn()` | `tokio::spawn()` |

## 三、全面横向对比

### 3.1 基础属性对比

| 维度 | 进程 | 线程 | 协程 |
|------|------|------|------|
| **调度方式** | 内核抢占式 | 内核抢占式 | 用户态协作式 |
| **地址空间** | 独立（互不可见） | 共享（同进程内） | 共享（同进程内） |
| **切换方式** | 内核态切换 + TLB 刷新 | 内核态切换 | 纯用户态切换 |
| **切换开销** | ~10-100 微秒 | ~1-10 微秒 | ~10-100 纳秒 |
| **创建成本** | ~100μs-数ms | ~1-10 微秒 | ~100 纳秒 |
| **单个内存开销** | ~2-5 MB（独立地址空间） | ~2-8 MB（独立栈） | ~几百字节到几 KB |
| **可创建数量** | 数百 | 数千 | 数十万 |
| **通信方式** | IPC（管道、消息队列等） | 共享内存 + 同步原语 | 共享内存（通常无需锁） |
| **隔离性** | 最强（崩溃不蔓延） | 弱（影响整个进程） | 弱（影响同一任务） |
| **编程复杂度** | 最简单 | 中等 | 较复杂 |

### 3.2 本项目实现对比

| 维度 | 进程爬虫 | 线程爬虫 | 协程爬虫 |
|------|---------|---------|---------|
| **源文件** | `process_crawler.rs` | `thread_crawler.rs` | `async_crawler.rs` |
| **代码行数** | 123 行 | 138 行 | 187 行 |
| **HTTP 客户端** | curl（外部进程） | ureq（进程内库） | ureq + spawn_blocking |
| **并发方式** | 串行（一个接一个） | 全部并行（33 个同时） | 受控并行（最多 20 个） |
| **结果收集** | 主循环直接记录 | mpsc::channel | Vec + handle.await |
| **并发限制** | 无（串行） | 无（全部启动） | Semaphore(20) |
| **需要的依赖** | 系统安装 curl | ureq | ureq + tokio |

## 四、执行流程对比

为了直观理解三者的差异，假设爬取 5 个学校（简化版），每个请求耗时如下：

```
学校A: 200ms    学校B: 300ms    学校C: 150ms    学校D: 400ms    学校E: 250ms
```

### 4.1 进程爬虫（串行执行）

```
时间(ms):  0    200   500   650   1050  1300
           |     |     |     |     |     |
主进程:    [curl-A][curl-B][curl-C][curl-D][curl-E]
           200ms  300ms  150ms  400ms  250ms

总耗时 = 200 + 300 + 150 + 400 + 250 = 1300ms
吞吐率 = 5 / 1.3s ≈ 3.8 请求/秒
```

**特点**：一个做完才做下一个。总时间是所有请求的**累加**。

### 4.2 线程爬虫（全部并发）

```
时间(ms):  0         150  200  250  300      400
           |          |    |    |    |        |
线程1(A):  [───── 200ms ─────]
线程2(B):  [────────── 300ms ──────────]
线程3(C):  [─── 150ms ──]
线程4(D):  [──────────────── 400ms ───────────────]
线程5(E):  [──────── 250ms ────────]

总耗时 = max(200, 300, 150, 400, 250) = 400ms
吞吐率 = 5 / 0.4s = 12.5 请求/秒
```

**特点**：所有线程同时启动，总时间取决于**最慢的那个**。比串行快了 3 倍多！

### 4.3 协程爬虫（受控并发，假设 Semaphore=3）

```
时间(ms):  0         150  200  250  300      400       550
           |          |    |    |    |        |         |
task-A:    [───── 200ms ─────]
task-B:    [────────── 300ms ──────────]
task-C:    [─── 150ms ──]
task-D:    [等待permit][──────── 400ms ────────────────]
task-E:              [等待][──────── 250ms ────────]
                      ↑ C完成释放permit，D获取permit
                           ↑ A完成释放permit，E获取permit

总耗时 ≈ 550ms（比全部并发慢一点，但控制了并发数）
吞吐率 = 5 / 0.55s ≈ 9.1 请求/秒
```

**特点**：用 Semaphore 限制了最大并发数，牺牲一点速度换取稳定性和礼貌性。

### 4.4 时间对比图

```
              0ms        500ms       1000ms      1300ms
              |           |           |           |
进程(串行):  [████████████████████████████████████] 1300ms
线程(全并发): [██████]                               400ms
协程(限并发): [█████████]                             550ms

               快 ←───────────────────────────→ 慢
```

## 五、性能预期分析

### 5.1 延迟分析

| 指标 | 进程爬虫 | 线程爬虫 | 协程爬虫 |
|------|---------|---------|---------|
| **单个请求延迟** | HTTP 往返时间 + 进程创建开销 | HTTP 往返时间 | HTTP 往返时间 + spawn_blocking 调度 |
| **总耗时** | Σ(所有请求) 串行累加 | ≈ max(所有请求) | ≈ max(所有请求) × (33/20) |
| **额外开销来源** | 进程创建/销毁 ~100μs/次 | 线程创建 ~5μs/次 | 任务创建 ~100ns/次 |

**关键洞察**：

- 进程爬虫慢不是因为"进程本身慢"，而是因为本实现是**串行**的
- 线程和协程的总耗时主要取决于**网络速度**，而不是并发模型的开销
- 协程的 Semaphore(20) 限制意味着总耗时会比线程稍长（因为不是 33 个全部同时）

### 5.2 吞吐率分析

```
吞吐率 = 请求数 / 总耗时

假设每个 HTTP 请求平均 500ms：

进程（串行）: 33 / (33 × 0.5s) = 2.0 请求/秒
线程（全并发）: 33 / 0.5s = 66 请求/秒（理想值，实际受网络带宽限制）
协程（20并发）: 33 / (0.5s × ceil(33/20)) = 33 / 1.0s = 33 请求/秒
```

### 5.3 内存开销分析

| 爬虫类型 | 每个执行单元内存 | 33 个任务总内存 | 说明 |
|---------|----------------|---------------|------|
| **进程** | ~2-5 MB/进程 | 串行所以只有 1 个 | curl 进程在完成后释放 |
| **线程** | ~2-8 MB/线程栈 | ~66-264 MB | 33 个线程栈同时存在 |
| **协程** | ~几百字节/任务 | ~几十 KB | 极其轻量 |

**注意**：
- 进程爬虫因为是串行执行，任何时刻只有 1 个 curl 进程在运行，实际内存开销最小
- 线程的栈空间可以通过 `thread::Builder::new().stack_size()` 调小
- 协程的内存效率在任务数量很大时优势明显（上万个任务时差距数量级）

### 5.4 资源消耗全景图

```
                       内存占用
                         ↑
                    264MB │        × 线程（33×8MB栈）
                         │
                         │
                         │
                    50MB  │            × 协程+阻塞线程池
                         │
                     5MB  │   × 进程（串行，只1个curl）
                         │
                         └──────────────────────────→ 并发数
                             1        20       33

                       总耗时
                         ↑
                  ~16.5s  │ × 进程（33×500ms串行）
                         │

                   ~1.0s  │            × 协程（20并发）
                   ~0.5s  │                      × 线程（33全并发）

## 七、决策指南 — 什么时候选哪个？

### 7.1 快速决策流程图

```
你要做什么？
│
├── 需要调用外部命令行工具（ffmpeg、curl 等）
│   └── → 进程
│
├── 需要极强的故障隔离（一个崩溃不能影响其他）
│   └── → 进程
│
├── 并发任务数量 < 100
│   ├── 已有同步阻塞代码，不想改 → 线程
│   ├── 纯 CPU 密集计算 → 线程
│   └── I/O 密集型 → 线程或协程都行
│
├── 并发任务数量 > 1000
│   └── → 协程（线程撑不住这么多）
│
├── 并发任务数量 100-1000
│   ├── I/O 密集型（网络请求、文件读写）→ 协程
│   └── CPU 密集型（计算、编码）→ 线程
│
└── 不确定？
    └── → 线程（最简单，以后需要再改协程）
```

### 7.2 场景推荐表

| 场景 | 推荐 | 原因 |
|------|------|------|
| 爬取 10 个网页 | 线程 | 数量少，线程够用，代码简单 |
| 爬取 10000 个网页 | 协程 | 线程开不了这么多，协程轻松支撑 |
| 视频批量转码 | 进程 | 调用 ffmpeg 外部工具 |
| Web 服务器 | 协程 | 需要处理大量并发连接 |
| 科学计算（矩阵运算） | 线程 | CPU 密集型，利用多核 |
| 数据库批量导入 | 线程/协程 | 取决于并发量和 I/O 占比 |
| 微服务 API 聚合 | 协程 | 同时调用多个 API 等待响应 |
| 安全沙箱（运行不可信代码） | 进程 | 需要内存隔离 |
| 已有大量同步代码 | 线程 | 不需要改成 async，直接 spawn |

### 7.3 本项目的选择分析

我们的爬虫任务特点：
- 33 个网站（中等数量）
- I/O 密集型（主要时间在等待 HTTP 响应）
- 对隔离性没有特殊要求

| 方案 | 是否适合本场景 | 分析 |
|------|-------------|------|
| 进程（串行） | 不太适合 | 串行执行太慢，但展示了进程隔离性 |
| 线程 | 适合 | 33 个线程完全在承受范围内，代码简单 |
| 协程 | 最适合 | Semaphore 控制并发，内存效率高，可扩展到更多网站 |

**如果只能选一个用于生产环境**：线程方案（简单、够用、可维护）或协程方案（更专业、可扩展），取决于团队对 async/await 的熟悉程度。

## 八、三种模型的本质差异总结

### 8.1 一张表看完所有区别

| 如果把计算比作... | 进程 | 线程 | 协程 |
|-----------------|------|------|------|
| **餐厅** | 开分店 | 雇多个服务员 | 一个服务员同时照应多桌 |
| **工厂** | 建独立车间 | 同一车间多条生产线 | 一条生产线切换做不同产品 |
| **办公** | 独立公司 | 同一公司多个员工 | 一个高效员工多任务切换 |
| **本质** | OS 分配独立资源 | OS 调度共享资源 | 用户态调度共享资源 |

### 8.2 三句话记住

> **进程**：独立的办公室，安全但开店成本高。适合需要隔离或调外部工具的场景。
>
> **线程**：同一间办公室的多个员工，协作方便但人太多坐不下。适合中等规模并发。
>
> **协程**：超级高效的员工，等待时切换任务，一个人顶一万个。适合大规模 I/O 并发。
