# 三种爬虫实现：进程 vs 线程 vs 协程 — 性能对比报告

---

## 一、核心概念

### 1.1 进程（Process）

**进程**是操作系统进行资源分配和调度的基本单位。每个进程拥有独立的虚拟地址空间（代码段、数据段、堆、栈）、文件描述符表、信号处理等内核资源。进程之间完全隔离，一个进程崩溃不会影响其他进程。

- 典型接口：
  - Linux: `fork()` / `exec*()`
  - Windows: `CreateProcess()`
  - Rust: `std::process::Command`

进程间通信（IPC）需要借助管道、消息队列、共享内存、信号量、Socket 等内核机制，开销较大。

### 1.2 线程（Thread）

**线程**是 CPU 调度的基本单位，是进程内的一个执行流。同一进程内的所有线程共享虚拟地址空间（堆、全局数据、文件描述符），但各自拥有独立的栈和寄存器上下文。由于共享地址空间，线程间通信可以直接通过共享变量，无需内核介入，但需要同步原语（互斥锁、信号量、条件变量）保护临界区。

- 典型接口：
  - POSIX: `pthread_create()`
  - Linux: `clone()`（轻量级进程）
  - Rust: `std::thread::spawn()`

### 1.3 协程（Coroutine / Async）

**协程**是比线程更轻量的用户态执行单元。协程的调度由用户态运行时（如 tokio、async-std）控制，而非操作系统内核。多个协程复用少量 OS 线程，在 I/O 等待时主动让出执行权（yield），从而实现高并发。

- Rust 中的协程基于 `async/await` 语法和 `Future` trait，是编译期生成的状态机。
- 协程切换完全在用户态完成，不需要陷入内核，开销远小于线程切换（~几纳秒 vs ~几微秒）。
- 典型运行时：tokio（多线程工作窃取）、async-std。

### 1.4 三者核心区别

| 维度       | 进程 (Process)            | 线程 (Thread)             | 协程 (Async/Coro)       |
|------------|--------------------------|--------------------------|-------------------------|
| 调度者     | 操作系统内核             | 操作系统内核             | 用户态运行时            |
| 地址空间   | 独立                     | 共享（进程内）            | 共享（进程内）           |
| 切换开销   | 最大（~数十µs，含TLB刷新） | 中等（~数µs，内核态切换） | 最小（~数ns，纯用户态）  |
| 内存开销   | 最大（独立页表、栈等）    | 中等（默认栈 ~2-8MB）     | 最小（仅需保存Future状态）|
| 通信方式   | IPC（管道/消息队列/Socket）| 共享内存 + 同步原语      | 共享内存（任务间无需锁）  |
| 隔离性     | 最强，故障不蔓延          | 弱，崩溃影响整个进程      | 弱，panic影响任务        |
| 创建数量   | 数百                     | 数千                     | 数十万                  |
| Rust 实现  | `std::process::Command`  | `std::thread::spawn()`   | `tokio::spawn()` / `async`|

## 二、爬虫程序的架构差异

### 2.1 进程爬虫

每个学校URL由一个独立的子进程处理。本实现中，主进程**顺序**启动 `curl` 子进程，每个子进程下载一个网页后退出，主进程收集其输出和退出状态。

**特点**：
- 每次请求是一个全新的进程，拥有完全独立的地址空间
- 进程创建开销大（fork + exec），内存开销大
- 天然隔离，curl 崩溃不影响主程序
- 本实现为**串行执行**（逐个启动并等待），这是进程模型在"并发爬虫"场景下的典型简化

```
主进程 ──启动──> curl子进程1 ──完成──> 收集结果 ──启动──> curl子进程2 ──...──> 完成
```

### 2.2 线程爬虫

每个学校URL由一个独立线程处理。主线程创建33个线程（每个学校一个），然后等待所有线程完成。各线程通过 `mpsc::channel` 将结果发送回主线程。

**特点**：
- 所有线程共享地址空间，无需 IPC
- 线程创建和切换由内核调度，开销中等
- 33个线程并发执行 HTTP 请求（网络I/O），I/O期间线程被内核挂起
- 线程数量固定且可控

```
主线程 ──spawn──> 线程1 ┐
        ──spawn──> 线程2 ├── 并发执行 ──> channel收集结果
        ──spawn──> ...   │
        ──spawn──> 线程33┘
```

### 2.3 协程爬虫

使用 tokio 异步运行时。33个学校URL分别被包装为 `tokio::task`，在 tokio 的工作线程池上并发执行。使用 `Semaphore` 限制最大并发数为20。

**特点**：
- 协程是用户态轻量任务，创建和切换开销极小
- HTTP 请求（网络 I/O）通过 `spawn_blocking` 放到阻塞线程池执行，不阻塞异步工作线程
- 协程数量可以远超线程数量
- tokio 的工作窃取调度器自动负载均衡

```
tokio runtime:
  工作线程1: [task1] [task4] [task7] ...
  工作线程2: [task2] [task5] [task8] ...
  ...
  阻塞线程池: [HTTP请求1] [HTTP请求2] ...   ← 网络I/O
```

## 三、性能预期分析

### 3.1 延迟分布

| 指标     | 进程爬虫           | 线程爬虫               | 协程爬虫              |
|----------|--------------------|------------------------|-----------------------|
| 最小延迟 | 取决于单次HTTP RTT | 取决于单次HTTP RTT     | 取决于单次HTTP RTT    |
| 平均延迟 | 高（串行累加）     | 中（并发，但含调度开销） | 中（并发，调度开销小） |
| **总耗时** | **最大**（所有请求耗时之和） | **小**（约为最慢请求的时间） | **最小**（调度更高效） |

**关键原因**：进程爬虫在本实现中是**串行**的——必须等 curl1 完成才启动 curl2。因此：

- 进程总耗时 = Σ(每个HTTP请求时间 + 进程创建开销)
- 线程/协程总耗时 ≈ max(每个HTTP请求时间) + 调度开销

### 3.2 吞吐率

进程爬虫的吞吐率受限于串行执行，预期在 **0.1-1 请求/秒**。线程和协程爬虫受益于并发，预期在 **1-10 请求/秒**（受限于网速和服务器响应时间）。

### 3.3 内存开销

| 爬虫类型     | 每个执行单元内存  | 典型总内存增量 |
|-------------|------------------|---------------|
| 进程 (curl) | ~2-5 MB/进程      | ~60-150 MB（33个curl进程）|
| 线程        | ~8 MB/线程（默认栈）| ~264 MB（33线程×8MB）    |
| 协程        | ~数百字节/协程     | ~10-50 MB                |

**注意**：实际内存开销受操作系统、curl 版本、Linux 写时复制（COW）等因素影响，线程栈可以通过 `thread::Builder` 调小（如 64KB），协程的内存效率最优。

## 四、具体例子说明差异

假设有 3 个网站，每个网站 HTTP 请求耗时分别为：

- 北京大学：200ms
- 清华大学：300ms
- 浙江大学：400ms

### 进程爬虫（串行）
```
时间线: |--curl-北大(200ms)--|--curl-清华(300ms)--|--curl-浙大(400ms)--|
总耗时: 200 + 300 + 400 = 900ms
```

### 线程爬虫（并发）
```
线程1: |--HTTP请求 北大(200ms)-------------|
线程2: |--HTTP请求 清华(300ms)--------------------|
线程3: |--HTTP请求 浙大(400ms)-----------------------------|
                              ↑ 所有线程并发执行
总耗时: max(200, 300, 400) = 400ms
```

### 协程爬虫（并发，调度更高效）
```
tokio worker-1: [setup 北大] -> (I/O等待) -> [parse 北大]
tokio worker-2: [setup 清华] -> (I/O等待) -> [parse 清华]
tokio worker-3: [setup 浙大] -> (I/O等待) -> [parse 浙大]
    阻塞线程:   [HTTP 北大]    [HTTP 清华]    [HTTP 浙大]
总耗时: max(200, 300, 400) ≈ 400ms（调度开销 < 线程）
```

## 五、适用场景总结

| 场景                      | 推荐方案 | 原因                                   |
|--------------------------|---------|---------------------------------------|
| CPU密集型计算（如视频编码）| 进程    | 绕过 GIL，充分利用多核                  |
| I/O密集型、请求数多       | 协程    | 内存效率高，可支撑大规模并发             |
| I/O密集型、请求数适中     | 线程    | 编程模型简单，无需异步运行时             |
| 高安全隔离需求            | 进程    | 进程间内存隔离，崩溃不影响其他           |
| 已有同步阻塞代码          | 线程    | 无需改造为 async，直接 spawn_thread 即可 |
