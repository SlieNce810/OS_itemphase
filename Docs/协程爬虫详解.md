## 一、什么是协程？

### 1.1 用生活比喻理解

在前面的文档中，我们用了这些比喻：
- **进程** = 独立的公司，有自己的办公室
- **线程** = 同一公司里的多个员工，共享办公室

现在来看**协程**：

想象一个**超级高效的员工**。他同时接了 33 个客户的订单（33 个爬取任务），但他只有一个人（或几个人，对应少量 OS 线程）。他是怎么做到"同时"处理这么多任务的？

```
小明（协程调度器）的一天：

09:00  拿起客户A的订单，给供应商打电话下单 ← 发起 HTTP 请求
09:01  电话还在等接通中...不干等着！          ← 遇到 I/O 等待
       → 放下电话，拿起客户B的订单           ← 切换到另一个任务
09:02  给客户B的供应商发邮件                  ← 发起另一个 HTTP 请求
09:03  邮件发出去了，等回复...不干等着！
       → 拿起客户C的订单                     ← 再切换
09:05  客户A的电话接通了！                    ← I/O 完成通知
       → 回到客户A的订单，继续处理            ← 恢复之前的任务
09:06  客户A搞定，客户B的邮件也回了
       → 处理客户B的订单
       ...
```

关键insight：**小明并没有同时做多件事**，他只是在一件事"等待"的时候去做另一件事。这种"遇到等待就切换"的策略就是协程的核心思想。

### 1.2 技术定义

**协程（Coroutine）** 是一种用户态的轻量级执行单元。与线程不同，协程的调度不由操作系统内核控制，而是由用户态的**运行时（Runtime）** 管理。

核心特点：
- **协作式调度**：协程主动让出执行权（在 `await` 点让出），而不是被操作系统强制中断
- **极其轻量**：一个协程只需要几百字节到几 KB 的内存（对比线程的 2-8MB）
- **运行在线程之上**：多个协程复用少量操作系统线程

在 Rust 中，协程通过 `async/await` 语法实现：
- `async fn` 定义一个异步函数，它返回一个 `Future`（未来值——可以理解为"一个承诺：这个结果还没算出来，但将来会有"）
- `await` 等待一个 `Future` 完成，如果还没完成就让出执行权
- 关于 Future 的详细原理，请看[第五节](#五asyncawait-在-rust-中如何工作)

### 1.3 三者的关系 — 一图看懂

```
操作系统层面                用户空间层面

┌─────────────────────────────────────────────┐
│                操作系统内核                    │
│                                             │
│  CPU核心1    CPU核心2    CPU核心3   CPU核心4  │
│    ↕           ↕           ↕          ↕     │
│  ┌─────┐   ┌─────┐   ┌─────┐   ┌─────┐   │
│  │线程1│   │线程2│   │线程3│   │线程4│   │
│  └─────┘   └─────┘   └─────┘   └─────┘   │
│   ↑ 内核调度（抢占式，几微秒一次切换）         │
└───────────────┬─────────────────────────────┘
                │
                ↓
┌─────────────────────────────────────────────┐
│        Tokio 运行时（用户空间）               │
│                                             │
│  线程1上运行:     线程2上运行:                 │
│  ┌───┐ ┌───┐    ┌───┐ ┌───┐               │
│  │协 │ │协 │    │协 │ │协 │               │
│  │程 │ │程 │    │程 │ │程 │               │
│  │A  │ │B  │    │C  │ │D  │  ...          │
│  └───┘ └───┘    └───┘ └───┘               │
│   ↑ 用户态调度（协作式，几十纳秒一次切换）      │
│   ↑ 每个协程只有几百字节                      │
└─────────────────────────────────────────────┘
```

## 二、协程与线程的本质区别

### 2.1 调度方式不同

这是最核心的区别。

| 特性 | 线程（抢占式调度） | 协程（协作式调度） |
|------|-------------------|-------------------|
| **谁来切换** | 操作系统内核 | 用户态运行时（如 Tokio） |
| **什么时候切换** | 内核定时器中断（时间片用完）或 I/O 等待 | 遇到 `.await` 时主动让出 |
| **可预测性** | 任何时刻都可能被切换（不可预测） | 只在 `.await` 点切换（可预测） |
| **切换开销** | ~1-10 微秒（需要陷入内核态） | ~10-100 纳秒（纯用户态操作） |

用比喻来解释：

```
线程 = 老师点名回答问题（抢占式）
  老师（操作系统）说："时间到！下一个同学来答。"
  你正在答题答到一半，也必须停下来。
  老师完全控制谁什么时候说话。

协程 = 自由讨论（协作式）
  每个同学（协程）主动说："我说完了 / 我需要等一下，你们先说。"
  只有在同学主动让出时，才切换到下一个人。
  如果一个同学一直说不停（不 await），其他人就没机会说话。
```

### 2.2 内存占用不同

```
一个线程的内存开销：
┌──────────────────────────────┐
│         线程栈               │
│    默认 2MB - 8MB            │ ← 即使只用了一小部分，也要预留这么多
│    （预分配，固定大小）        │
│                              │
│    函数调用记录               │
│    局部变量                   │
│    ...                       │
└──────────────────────────────┘

一个协程（Future）的内存开销：
┌──────────────┐
│ Future 状态   │
│ ~几百字节     │ ← 只保存 await 点之间需要的变量
│ 到几 KB       │    没有预分配的栈空间
└──────────────┘
```

数字对比：

| 数量 | 线程占用的栈空间 | 协程占用的空间 |
|------|-----------------|---------------|
| 100 | 200 MB - 800 MB | ~100 KB |
| 1,000 | 2 GB - 8 GB | ~1 MB |
| 10,000 | 20 GB - 80 GB | ~10 MB |
| 100,000 | 不可能 | ~100 MB |

这就是为什么高并发场景下必须使用协程——线程根本开不了那么多。

### 2.3 创建和切换成本不同

```
创建一个线程：
1. 向操作系统申请（系统调用，切换到内核态）
2. 分配栈空间（2-8MB）
3. 初始化线程上下文
4. 加入内核调度队列
耗时：~1-10 微秒

创建一个协程（tokio::spawn）：
1. 创建一个 Future 对象（堆上分配几百字节）
2. 放入运行时的任务队列
耗时：~100 纳秒

差距：10-100 倍
```

## 三、事件循环与非阻塞 I/O

### 3.1 为什么协程需要非阻塞 I/O？

要理解协程，必须先理解**阻塞**和**非阻塞**的区别。

```
阻塞 I/O（线程模型使用的方式）：

线程: [发起HTTP请求] ──── 干等 ──── 干等 ──── 干等 ──── [收到响应] → 继续工作
                         ↑ 这段时间线程被操作系统挂起
                           什么都不做，白白浪费一个线程


非阻塞 I/O（协程模型使用的方式）：

协程A: [发起HTTP请求] → "我先等着，你们先"（yield）
                         ↓
协程B:                   [发起HTTP请求] → "我也等着"（yield）
                                          ↓
协程C:                                    [发起HTTP请求] → ...
                         ↓
       [A的响应到了！] → 协程A恢复执行
                                          ↓
                                    [C的响应到了！] → 协程C恢复执行
```

### 3.2 事件循环 (Event Loop)

事件循环是协程运行时的"大脑"，它不停地做以下事情：

```
┌──────────────────────────────────────────────────┐
│                  事件循环（简化版）                 │
│                                                  │
│  loop {                                          │
│      // 1. 检查有没有就绪的事件                     │
│      //    （I/O完成、定时器到期等）                  │
│      events = poll_events();                     │
│                                                  │
│      // 2. 唤醒等待这些事件的协程                    │
│      for event in events {                       │
│          wake_up(event.associated_task);          │
│      }                                           │
│                                                  │
│      // 3. 运行所有就绪的协程                       │
│      //    直到它们再次遇到 await（让出）             │
│      for task in ready_tasks {                   │
│          task.poll();  // 执行到下一个 await        │
│      }                                           │
│  }                                               │
└──────────────────────────────────────────────────┘
```

用餐厅的比喻：

```
服务员（事件循环）的工作：

1. 看看厨房（I/O 事件）有没有做好的菜 → 如果有，端到对应的桌子
2. 看看有没有新客人（新任务）举手点菜 → 如果有，去给他们点菜
3. 看看有没有客人吃完了 → 如果有，去结账

服务员不会站在厨房门口干等一道菜做好——
他会一边等一边服务其他桌的客人。

这就是事件循环的效率所在！
```

## 四、Tokio 运行时原理

### 4.1 什么是 Tokio？

Tokio 是 Rust 最流行的异步运行时。它提供了：

1. **多线程事件循环**：在多个 OS 线程上运行事件循环
2. **任务调度器**：管理和调度所有协程（异步任务）
3. **异步 I/O 原语**：异步的 TCP/UDP、文件操作、定时器等
4. **阻塞线程池**：专门运行无法异步化的阻塞操作

### 4.2 Tokio 的架构

```
┌─────────────────────────────────────────────────────────┐
│                    Tokio 运行时                           │
│                                                         │
│  ┌─────────────────────────────────────────┐            │
│  │        工作线程池（Worker Threads）        │            │
│  │   默认数量 = CPU 核心数                    │            │
│  │                                         │            │
│  │  线程1        线程2        线程3   ...   │            │
│  │  ┌─────┐     ┌─────┐     ┌─────┐       │            │
│  │  │任务队列│   │任务队列│   │任务队列│      │            │
│  │  │[T1]  │   │[T4]  │   │[T7]  │      │            │
│  │  │[T2]  │   │[T5]  │   │[T8]  │      │            │
│  │  │[T3]  │   │[T6]  │   │[T9]  │      │            │
│  │  └─────┘     └─────┘     └─────┘       │            │
│  │                                         │            │
│  │  工作窃取：如果线程1空闲，会从线程2偷任务   │            │
│  └─────────────────────────────────────────┘            │
│                                                         │
│  ┌─────────────────────────────────────────┐            │
│  │        阻塞线程池（Blocking Threads）      │            │
│  │   用于运行 spawn_blocking 中的阻塞任务     │            │
│  │                                         │            │
│  │  阻塞线程1    阻塞线程2    阻塞线程3 ...  │            │
│  │  [ureq HTTP]  [文件写入]   [HTML解析]    │            │
│  └─────────────────────────────────────────┘            │
│                                                         │
│  ┌─────────────────────────────────────────┐            │
│  │        I/O 驱动（epoll/kqueue/IOCP）      │            │
│  │   监控所有非阻塞 I/O 事件                  │            │
│  └─────────────────────────────────────────┘            │
└─────────────────────────────────────────────────────────┘
```

### 4.3 工作窃取调度器

Tokio 使用**工作窃取（Work Stealing）** 算法来负载均衡：

```
正常情况：每个工作线程处理自己队列中的任务

  线程1的队列: [T1] [T2] [T3]
  线程2的队列: [T4] [T5] [T6]
  线程3的队列: [T7]              ← 任务少
  线程4的队列: []                 ← 空闲了！

工作窃取：空闲的线程从忙碌的线程"偷"任务

  线程4: "我空闲了，让我看看谁最忙..."
  线程4: 从线程1偷走 [T3]
  
  结果：
  线程1的队列: [T1] [T2]
  线程4的队列: [T3]              ← 偷到了！开始干活
```

这保证了所有 CPU 核心都能被充分利用，不会出现某些核心忙死、某些核心闲死的情况。

### 4.4 `#[tokio::main]` 做了什么？

```rust
// 你写的代码：
#[tokio::main]
async fn main() {
    // ...
}

// 宏展开后实际等价于：
fn main() {
    let runtime = tokio::runtime::Builder::new_multi_thread()
        .enable_all()             // 启用 I/O 和定时器驱动
        .build()                  // 构建运行时
        .unwrap();
    
    runtime.block_on(async {
        // 你的 async main 代码在这里运行
    });
    // 运行时自动清理和关闭
}
```

所以 `#[tokio::main]` 做了三件事：
1. 创建一个多线程的 Tokio 运行时
2. 把你的 `async main()` 作为第一个任务放到运行时上执行
3. 等待所有任务完成后自动关闭运行时

## 五、async/await 在 Rust 中如何工作

### 5.1 async fn 是什么？

当你写 `async fn foo() -> i32 { ... }` 时，Rust 编译器会做一件神奇的事——把你的代码变成一个**状态机**。

**什么是状态机？** 状态机就是一个"有记忆的开关"。想象一个自动售货机：
- 状态1：等待投币 → 投币后切换到状态2
- 状态2：等待选择商品 → 选择后切换到状态3
- 状态3：出货 → 完成后回到状态1

每个状态记住了"当前做到了哪一步"和"下一步该做什么"。异步函数也是一样——每个 `.await` 就是一个状态切换点。

```rust
// 你写的代码：
async fn download(url: &str) -> String {
    let response = http_get(url).await;  // 等待 HTTP 响应
    response.body().await                 // 等待读取响应体
}

// 编译器实际生成的（简化版）：
// 一个状态机！每个 await 是一个状态切换点
enum DownloadFuture {
    // 状态0：初始状态，还没开始
    Start { url: String },
    
    // 状态1：已经发起 HTTP 请求，等待响应（对应第一个 .await）
    WaitingForResponse { pending_request: HttpFuture },
    
    // 状态2：已收到响应，等待读取 body（对应第二个 .await）
    WaitingForBody { pending_body: BodyFuture },
    
    // 状态3：完成
    Done,
}
```

每个 `.await` 点就是一个状态切换点。编译器把你的异步函数变成了一个**状态机**。

### 5.2 await 做了什么？

```rust
let result = some_future.await;
```

这行代码的含义：

```
1. 检查 some_future 是否已经完成
   ├── 如果完成了 → 取出结果，继续执行下一行代码
   └── 如果没完成 → 保存当前状态，让出执行权给调度器
                    调度器去运行其他就绪的任务
                    等 some_future 完成后，调度器会恢复这个任务
```

用图来表示：

```
协程A执行：
  ┌─────┐     ┌──────────┐     ┌─────┐
  │代码1 │ →  │ await X  │ →  │代码2 │ →  ...
  └─────┘     └────┬─────┘     └─────┘
                   │
              X没完成？
                   │
                   ↓
              ┌─────────┐
              │暂停协程A │ → 保存状态到 Future 结构体中
              │切换到B  │ → 调度器选择下一个就绪的协程
              └─────────┘
                   │
              (等X完成)
                   │
                   ↓
              ┌──────────┐
              │X完成了！  │ → 调度器恢复协程A
              │恢复协程A │ → 从保存的状态继续执行
              └──────────┘
                   │
                   ↓
              继续执行代码2
```

### 5.3 为什么 async/await 比回调更好？

在 async/await 出现之前，异步编程主要用"回调"风格：

```
// 回调地狱（Callback Hell）——难以阅读和维护
http_get(url1, |response1| {
    parse(response1, |data1| {
        http_get(url2, |response2| {
            parse(response2, |data2| {
                save(data1, data2, |result| {
                    println!("Done: {}", result);
                });
            });
        });
    });
});

// async/await 风格——像同步代码一样清晰
async fn do_work() {
    let response1 = http_get(url1).await;
    let data1 = parse(response1).await;
    let response2 = http_get(url2).await;
    let data2 = parse(response2).await;
    let result = save(data1, data2).await;
    println!("Done: {}", result);
}
```

async/await 让异步代码看起来像同步代码，但执行时有协程切换的高效性。

## 六、本项目的协程爬虫实现

### 6.1 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│                    Tokio 运行时                                │
│                                                              │
│  ┌────────────────────────────────────────────┐              │
│  │              run_async() 协调函数            │              │
│  │                                            │              │
│  │  Semaphore (20个许可证)                      │              │
│  │  ┌───────────────────────────────────┐     │              │
│  │  │ ████████████████████ (20个位置)     │     │              │
│  │  └───────────────────────────────────┘     │              │
│  │                                            │              │
│  │  33个异步任务：                              │              │
│  │  task1 → acquire permit → crawl → release  │              │
│  │  task2 → acquire permit → crawl → release  │              │
│  │  ...                                       │              │
│  │  task33 → [等待permit] → crawl → release   │              │
│  └────────────────────────────────────────────┘              │
│                                                              │
│  ┌────────────────────────────────────────────┐              │
│  │            阻塞线程池                        │              │
│  │                                            │              │
│  │  [ureq HTTP 请求]  [HTML解析]  [文件写入]   │              │
│  │  因为 ureq 是同步库，必须在阻塞线程池中运行   │              │
│  └────────────────────────────────────────────┘              │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 执行时间线

```
时间 ──────────────────────────────────────────────────────────→

Semaphore容量=20

task1:  [取permit][──spawn_blocking(HTTP)──][parse][write][释放permit]
task2:  [取permit][────spawn_blocking(HTTP)────][parse][write][释放]
task3:  [取permit][──spawn_blocking(HTTP)──][parse][write][释放permit]
...
task20: [取permit][──────spawn_blocking(HTTP)──────][parse][write][释放]
task21: [等待....][取permit][──spawn_blocking(HTTP)──][parse][write][释放]
task22: [等待........][取permit][──spawn_blocking(HTTP)──][parse][write][释放]
...
task33: [等待............][取permit][─spawn_blocking(HTTP)─][parse][write][释放]

        ↑                ↑
        前20个立即开始     后13个必须等前面的释放permit后才能开始
```

### 6.3 与线程爬虫的关键区别

| 维度 | 线程爬虫 | 协程爬虫 |
|------|---------|---------|
| **执行单元** | 33 个 OS 线程 | 33 个 tokio 任务 + 少量工作线程 |
| **并发控制** | 无限制（33 个全部并行） | Semaphore 限制最多 20 个同时执行 |
| **HTTP 客户端** | 直接在线程中调用 ureq | 通过 `spawn_blocking` 放到阻塞线程池 |
| **内存开销** | 33 × 2-8MB 栈 = 66-264MB | 33 个 Future ≈ 几十 KB + 阻塞线程池 |
| **调度方式** | 内核抢占式调度 | Tokio 协作式 + 工作窃取 |

### 7.1 导入部分

```rust
use std::time::{Duration, Instant};
use tokio::sync::Semaphore;          // Tokio 提供的异步信号量
//    ↑ 注意是 tokio::sync 而不是 std::sync
//    Tokio 的信号量支持 .await，不会阻塞线程

use crawler::common::{current_rss_kb, html_to_text, print_latency_stats, print_memory_stats};
use crawler::schools::{SchoolInfo, SCHOOLS};
```

### 7.2 `crawl_one_async` 函数 — 单个协程的爬取任务

```rust
async fn crawl_one_async(
//  ↑ async 关键字！这使得函数返回一个 Future 而不是直接返回值
//  调用时不会立即执行，需要 .await 或 tokio::spawn 才会真正开始
    school: &SchoolInfo,
    output_dir: &PathBuf,
) -> (String, f64, bool, usize) {
    let url = school.url.to_string();   // 克隆 URL 为 owned String
    //                                    因为 spawn_blocking 需要 'static 数据
    let name = school.name;              // &'static str，可以安全复制
    let filepath = output_dir.join(format!("{}.txt", name));

    let start = Instant::now();
```

#### 发起 HTTP 请求 — spawn_blocking

```rust
    // ★ 核心代码：用 spawn_blocking 在阻塞线程池中执行 HTTP 请求
    let result = tokio::task::spawn_blocking(move || {
        //                                   ↑ move: 将 url 的所有权转移到闭包中
        //       ↑ spawn_blocking: 把闭包丢到专门的阻塞线程池中运行
        //         不会阻塞当前的异步工作线程！
        ureq::get(&url)
            .timeout(Duration::from_secs(30))
            .set("User-Agent", "Mozilla/5.0 (compatible; Crawler/1.0)")
            .call()
        // ↑ ureq 是同步库，.call() 会阻塞当前线程
        //   但因为我们在 spawn_blocking 中，阻塞的是阻塞线程池的线程
        //   不影响 tokio 工作线程运行其他协程
    })
    .await;
    // ↑ .await: 当前协程在这里让出执行权
    //   等 spawn_blocking 中的任务完成后，协程会被唤醒继续执行
```

#### 处理结果 — 双层 Result

```rust
    let elapsed_ms = start.elapsed().as_secs_f64() * 1000.0;

    match result {
        // ★ 注意双层 Ok ！
        // 外层 Ok: spawn_blocking 本身成功（线程池没有出问题）
        // 内层 Ok: ureq 的 HTTP 请求成功
        Ok(Ok(response)) => {
            let html = response.into_string().unwrap_or_default();

            // HTML 转文本也用 spawn_blocking
            // 因为 html_to_text 是 CPU 密集型操作（正则表达式匹配）
            // 如果直接在异步上下文中执行，会阻塞工作线程
            let text = tokio::task::spawn_blocking(move || html_to_text(&html))
                .await
                .unwrap_or_default();
            //  ↑ 如果 spawn_blocking 失败，返回空字符串

            let content_len = text.len();

            // 文件写入也用 spawn_blocking
            // 因为 fs::write 是同步的阻塞 I/O
            let write_result = tokio::task::spawn_blocking(move || {
                fs::write(&filepath, &text)
            })
            .await;

            match write_result {
                Ok(Ok(_)) => (name.to_string(), elapsed_ms, true, content_len),
                _ => {
                    eprintln!("  写入文件失败: {}", name);
                    (name.to_string(), elapsed_ms, false, 0)
                }
            }
        }
        // 外层 Ok，内层 Err: HTTP 请求失败（网络错误、超时等）
        Ok(Err(error)) => {
            eprintln!("  请求失败 {}: {}", name, error);
            (name.to_string(), elapsed_ms, false, 0)
        }
        // 外层 Err: spawn_blocking 本身失败
        // 极其罕见——通常只在 Tokio 运行时正在关闭时发生
        Err(_) => {
            eprintln!("  spawn_blocking失败: {}", name);
            (name.to_string(), elapsed_ms, false, 0)
        }
    }
}
```

### 7.3 `run_async` 函数 — 协调所有协程

```rust
async fn run_async(
    output_dir: &PathBuf,
    concurrency: usize,    // 最大并发数，本项目中为 20
) -> Vec<(String, f64, bool, usize)> {
    
    // 创建信号量，控制最多同时有 concurrency 个任务在执行
    let semaphore = Arc::new(Semaphore::new(concurrency));
    //              ↑ Arc = Atomic Reference Counting（原子引用计数）
    //  为什么需要 Arc？因为多个 tokio 任务要共享同一个 Semaphore
    //  Arc 允许多个所有者共享同一个数据，且线程安全
    //
    //  类比：信号量是一个停车场的入口闸机，Arc 让所有车辆都能看到同一个闸机

    let mut handles = Vec::new();

    for school in SCHOOLS {
        let semaphore = semaphore.clone();
        //             ↑ clone Arc 只是增加引用计数（很便宜的操作）
        //               不是复制 Semaphore 本身
        let dir = output_dir.clone();

        let handle = tokio::spawn(async move {
            //       ↑ tokio::spawn: 创建一个新的异步任务
            //         与 thread::spawn 类似，但创建的是协程而不是 OS 线程
            //         成本极低（~100 纳秒 vs 线程的 ~1-10 微秒）
            
            let _permit = semaphore.acquire().await.unwrap();
            //            ↑ 尝试获取一个许可证
            //              如果 20 个许可证都被占了 → 当前任务暂停等待
            //              .await 在这里让出执行权！
            //              直到有任务释放许可证，当前任务才会被唤醒
            //
            // _permit 变量名以 _ 开头，表示"我知道它没被直接使用"
            // 但它的存在很重要！它实现了 Drop trait：
            // 当 _permit 离开作用域时，自动释放许可证回 Semaphore

            crawl_one_async(school, &dir).await
            // ↑ 执行实际的爬取任务
            
            // 函数返回时，_permit 被自动 drop → 许可证释放
            // 下一个等待许可证的任务会被唤醒
        });

        handles.push(handle);
    }

    // 等待所有任务完成，收集结果
    let mut results = Vec::new();
    for handle in handles {
        if let Ok(result) = handle.await {
            // ↑ 等待每个任务完成
            //   handle.await 返回 Result<T, JoinError>
            //   如果任务 panic 了，返回 Err(JoinError)
            results.push(result);
        }
    }

    results
}
```

### 7.4 `main` 函数

```rust
#[tokio::main]  // ← 这个宏创建 Tokio 运行时并运行 async main
async fn main() {
    let start_total = Instant::now();
    let mem_before = current_rss_kb();

    // 准备输出目录（与其他爬虫相同）
    let output_dir = {
        let mut dir = PathBuf::from(env!("CARGO_MANIFEST_DIR"));
        dir.pop();
        dir.push("Docs");
        dir.push("高校名称和官方网站");
        dir
    };
    fs::create_dir_all(&output_dir).expect("无法创建输出目录");

    let concurrency = 20;  // ★ 最大并发数
    //                       为什么是 20 而不是 33？
    //                       同时向 33 个服务器发请求可能：
    //                       1. 被防火墙/WAF 识别为攻击
    //                       2. 本地网络带宽不够
    //                       3. 本地 DNS 解析队列排满
    //                       限制为 20 是一个平衡——
    //                       足够并发以提高效率，又不至于太激进

    // 启动所有协程并等待完成
    let results = run_async(&output_dir, concurrency).await;

    // 以下为统计输出，与其他爬虫相同
    let total_time = start_total.elapsed();
    let mem_after = current_rss_kb();

    let mut total_success = 0usize;
    let mut total_fail = 0usize;
    let mut latencies: Vec<f64> = Vec::new();

    for (name, latency, success, content_len) in &results {
        if *success {
            total_success += 1;
            println!("✓ {} : 耗时 {:.0}ms, 文本长度 {} 字节", name, latency, content_len);
        } else {
            total_fail += 1;
            println!("✗ {} : 耗时 {:.0}ms", name, latency);
        }
        latencies.push(*latency);
    }

    println!("总请求数:       {}", SCHOOLS.len());
    println!("成功请求数:     {}", total_success);
    println!("失败请求数:     {}", total_fail);
    println!("总耗时:         {:.2} ms", total_time.as_secs_f64() * 1000.0);
    println!("吞吐率:         {:.2} 请求/秒",
             if total_time.as_secs_f64() > 0.0 {
                 SCHOOLS.len() as f64 / total_time.as_secs_f64()
             } else { 0.0 });

    print_latency_stats(&latencies);
    print_memory_stats(mem_before, mem_after);
}
```

## 八、Semaphore 信号量详解

### 8.1 什么是信号量？

信号量是一种计数型的同步原语。用停车场来比喻：

```
停车场（Semaphore）有 20 个车位（permits）

┌──────────────────────────────────────────┐
│    停车场（capacity = 20）                 │
│                                          │
│  [车1] [车2] [车3] ... [车20]            │ ← 20 辆车都停满了
│                                          │
└──────────────────────────────────────────┘
     入口闸机
        │
     [车21] [车22] ... [车33]               ← 这 13 辆车在外面排队等
        │
     当一辆车离开（release）→ 下一辆车进入（acquire）
```

### 8.2 信号量的操作

```
acquire()（获取许可证/进入停车场）：
  ├── 如果有空位（permits > 0）→ permits -= 1，立即通过
  └── 如果没空位（permits == 0）→ 排队等待

release()（释放许可证/离开停车场）：
  → permits += 1，如果有人在排队，唤醒一个
```

### 8.3 在本项目中的运行过程

```
时刻0: Semaphore(20), 33个任务全部创建

时刻1: task1-task20 各获取一个 permit → Semaphore(0)
       task21-task33 在 acquire().await 处等待

时刻2: task3 完成，释放 permit → Semaphore(1)
       task21 被唤醒，获取 permit → Semaphore(0)

时刻3: task7 完成，释放 permit → Semaphore(1)
       task22 被唤醒，获取 permit → Semaphore(0)

... 依此类推 ...

时刻N: 所有 33 个任务都完成了
```

### 8.4 为什么需要信号量而不是直接 spawn 33 个？

直接 spawn 33 个异步任务也**可以**工作，但不够"体贴"：

| 不用信号量 | 用信号量 |
|-----------|---------|
| 33 个请求同时发出 | 最多 20 个同时发出 |
| 可能被服务器认为是 DDoS 攻击 | 温和的请求速率 |
| 本地网络可能拥塞 | 网络负载更平稳 |
| 展示了"无限制并发" | 展示了"受控并发" |

在生产环境中，信号量是控制并发的标准做法。

## 九、spawn_blocking 详解

### 9.1 为什么需要 spawn_blocking？

这是本项目中最值得深入理解的设计决策。

**问题**：ureq 是一个同步（blocking）的 HTTP 库。当调用 `ureq::get(url).call()` 时，它会阻塞当前线程，直到 HTTP 响应返回。

**为什么阻塞是个大问题？**

```
如果直接在 async 函数中调用阻塞代码：

Tokio 工作线程1 上运行着协程A、B、C

协程A: [开始] → [调用 ureq.call()] ── 阻塞中 ── 阻塞中 ── [完成]
                       ↑
                 整个工作线程被阻塞！
                 协程B和C本来可以在这个线程上运行
                 现在它们也被卡住了！

如果所有工作线程都被阻塞 → 整个 Tokio 运行时停摆！
```

**解决方案**：`spawn_blocking` 把阻塞操作丢到**专门的阻塞线程池**中运行：

```
Tokio 工作线程1:
  协程A: [开始] → [spawn_blocking(ureq)] → .await → [继续处理]
                          ↓                    ↑
                   异步工作线程不阻塞           完成后唤醒
                   可以继续运行其他协程
                          ↓
阻塞线程池:
  阻塞线程X: [── ureq.call() 阻塞等待 ──] → 完成！通知协程A
```

### 9.2 本项目中有三处 spawn_blocking

```rust
// 第1处：HTTP 请求（网络 I/O 阻塞）
let result = tokio::task::spawn_blocking(move || {
    ureq::get(&url).timeout(...).call()
}).await;

// 第2处：HTML 转文本（CPU 密集型操作）
let text = tokio::task::spawn_blocking(move || {
    html_to_text(&html)    // 正则表达式匹配，可能耗时几十毫秒
}).await.unwrap_or_default();

// 第3处：文件写入（磁盘 I/O 阻塞）
let write_result = tokio::task::spawn_blocking(move || {
    fs::write(&filepath, &text)
}).await;
```

### 9.3 理想方案 vs 本项目方案

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **理想方案** | 使用异步 HTTP 库（如 `reqwest`） | 不需要 spawn_blocking，更高效；但需要额外的依赖 |
| **本项目方案** | 用 ureq + spawn_blocking | 代码稍复杂，但展示了"如何在异步代码中使用同步库" |

本项目选择 ureq + spawn_blocking 而不是 reqwest 是一个**教学决策**——它展示了现实中常见的问题：你可能有已有的同步代码，需要在异步上下文中使用。`spawn_blocking` 是解决这类问题的标准方法。

## 十、协程模型的优缺点

### 10.1 优点

| 优点 | 说明 | 在本项目中的体现 |
|------|------|----------------|
| **极轻量** | 每个协程只需几百字节内存 | 33 个任务几乎不占额外内存 |
| **高并发** | 可以创建数十万个协程 | 本项目只有 33 个，但架构可以支撑成千上万个 |
| **调度高效** | 用户态切换，纳秒级 | 协程切换不需要系统调用，极快 |
| **受控并发** | Semaphore 可以精确控制并发数 | 限制为 20 个并发请求，保护目标服务器 |
| **I/O 等待不浪费** | 等待时自动切换到其他任务 | HTTP 请求等待时，其他任务继续处理 |
| **充分利用 CPU** | 工作窃取调度器自动负载均衡 | Tokio 自动把任务分配到各个 CPU 核心 |

### 10.2 缺点

| 缺点 | 说明 | 在本项目中的体现 |
|------|------|----------------|
| **代码更复杂** | async/await 引入新的概念和语法 | 187 行代码（对比进程 123 行，线程 138 行） |
| **需要异步运行时** | 必须依赖 Tokio 等运行时库 | Cargo.toml 中需要 `tokio = { features = ["full"] }` |
| **阻塞代码需要包装** | 同步阻塞代码必须用 spawn_blocking | 三处 spawn_blocking 增加了代码复杂度 |
| **调试更困难** | 异步栈帧不如同步代码直观 | 错误信息可能涉及 Future、JoinError 等概念 |
| **双层 Result** | spawn_blocking 包装导致嵌套 Result | `Ok(Ok(response))` 这种模式初学者容易困惑 |
| **协作式调度的风险** | 如果忘记 await 或做了阻塞操作，会卡住整个工作线程 | 这就是为什么必须用 spawn_blocking |

### 10.3 什么时候不该用协程？

```
不适合 ✗
├── 纯 CPU 密集型计算（没有 I/O 等待，协程的切换优势发挥不出来）
├── 任务数很少（只有 3-5 个任务，线程就够了，不值得引入 Tokio）
├── 团队不熟悉 async/await（学习成本高，线程模型更直观）
└── 所有依赖库都是同步的（全部需要 spawn_blocking 包装，失去了协程的优势）
```

## 十一、适用场景

### 11.1 什么时候应该选择协程模型？

**场景一：高并发网络服务器**

> "我要写一个 Web 服务器，同时处理 10000 个客户端连接。"

这是协程最经典的应用场景。每个连接对应一个协程，10000 个协程只需要几 MB 内存。如果用线程，10000 个线程需要 20-80 GB 内存。

**场景二：大规模网络爬虫**

> "我要爬取 100000 个网页。"

协程 + 信号量可以精确控制并发请求数（比如限制 100 个），同时用极少的内存管理 100000 个任务。

**场景三：微服务间通信**

> "我的服务需要同时调用 5 个其他微服务的 API，然后聚合结果。"

协程可以轻松地并发调用多个 API，使用 `tokio::join!` 或 `futures::join_all` 等待所有结果。

**场景四：实时数据流处理**

> "我需要从多个数据源实时接收数据并处理。"

协程可以为每个数据源创建一个监听任务，当有数据到达时自动唤醒处理。

### 11.2 在本项目中为什么用协程？

1. **展示高效的并发模型**：对比线程，协程在内存和切换开销上有数量级的优势
2. **展示 Semaphore 并发控制**：信号量是生产级系统中控制并发的标准做法
3. **展示 spawn_blocking 的使用**：解决"异步上下文中使用同步库"这个现实问题
4. **展示 Tokio 运行时**：Tokio 是 Rust 异步生态的基石，理解它对 Rust 开发非常重要

## 十二、一句话记住

> **协程就像一个超级高效的员工——虽然只有一个人（几个线程），但他在等快递（I/O）的时候会去处理其他订单，一个人就能"同时"处理上万个任务。适合高并发 I/O 密集型场景，但代码比线程复杂。**
