## 前置知识 — 几个基础概念

在开始之前，先了解几个会反复出现的术语：

| 术语 | 含义 | 比喻 |
|------|------|------|
| **I/O（输入/输出）** | 程序与外部世界交换数据的操作，如网络请求、读写文件、键盘输入 | 寄信/收信 |
| **内核态 vs 用户态** | CPU 的两种运行模式。**内核态**拥有最高权限（能操作硬件、管理进程），**用户态**是普通程序运行的模式，权限受限。程序需要操作系统帮忙时（如创建进程、读写文件），要通过"系统调用"从用户态切换到内核态 | 普通员工（用户态）需要经理签字（内核态）才能动公章 |
| **PID（进程标识符）** | 操作系统给每个进程分配的唯一编号，就像每个人的身份证号 | 身份证号 |

这些概念在三篇详解文档中都会频繁出现。

## 一、什么是进程？

### 1.1 用生活比喻理解

想象一个大型写字楼里有很多家公司。每家公司（进程）都有自己**独立的办公室**（内存空间），有自己的**员工**（代码和数据），有自己的**门禁卡**（权限），有自己的**档案柜**（文件描述符）。

- 公司和公司之间**互不干扰**——A 公司倒闭了，B 公司照样运营。
- 公司之间想交流信息，不能直接走进对方办公室翻资料，必须通过**快递、电话或共享会议室**（进程间通信机制）。
- 开一家新公司（创建进程）成本很高——要装修办公室、配置设备、招聘人员。

这就是进程最核心的特点：**隔离性强，但创建和通信成本高**。

### 1.2 技术定义

**进程（Process）** 是操作系统进行资源分配的基本单位。当你运行一个程序时，操作系统会为它创建一个进程，分配以下资源：

- **独立的虚拟地址空间**：每个进程都"以为"自己独占了整台电脑的内存
- **程序代码和数据**：正在执行的机器指令和变量
- **系统资源**：打开的文件、网络连接、信号处理器等
- **进程控制块（PCB）**：内核维护的进程元数据（PID、状态、优先级等）

简单说：**进程 = 正在运行的程序 + 它所占用的全部资源**。

### 1.3 进程 vs 程序

很多初学者会混淆"程序"和"进程"，其实它们的关系就像"菜谱"和"炒菜"：

| 对比项 | 程序 (Program) | 进程 (Process) |
|--------|---------------|---------------|
| 本质   | 存储在磁盘上的文件 | 正在内存中运行的实例 |
| 状态   | 静态的，不会变化 | 动态的，有生命周期 |
| 数量   | 一份程序文件 | 可同时运行多个进程 |
| 举例   | `/usr/bin/curl` 这个文件 | 你运行 `curl http://example.com` 时创建的实例 |

同一个程序可以同时跑多个进程。比如你可以同时打开三个终端窗口，每个都运行 `curl`，就有三个 curl 进程在同时执行。

## 二、进程的内部结构

每个进程在内存中的布局可以简化为以下几个区域：

```
高地址 ┌─────────────────────┐
       │      内核空间        │ ← 用户程序不能直接访问
       ├─────────────────────┤
       │        栈 (Stack)    │ ← 局部变量、函数调用记录
       │         ↓            │    从高地址向低地址增长
       │                     │
       │        （空闲区）     │
       │                     │
       │         ↑            │
       │        堆 (Heap)     │ ← 动态分配的内存（如 Vec、String）
       ├─────────────────────┤    从低地址向高地址增长
       │    数据段 (Data)     │ ← 全局变量、静态变量
       ├─────────────────────┤
       │    代码段 (Text)     │ ← 机器指令（只读）
低地址 └─────────────────────┘
```

### 各区域的作用

| 区域 | 存什么 | 特点 |
|------|--------|------|
| **代码段 (Text)** | 编译后的机器指令 | 只读，多个相同进程可共享 |
| **数据段 (Data)** | 全局变量、`static` 变量 | 程序启动时就分配好 |
| **堆 (Heap)** | `Vec`、`String`、`Box` 等动态分配的数据 | 需要手动管理（Rust 通过所有权自动管理） |
| **栈 (Stack)** | 函数参数、局部变量、返回地址 | 自动管理，函数返回就释放 |

**关键点**：每个进程的这些区域是**完全独立的**。进程 A 的堆内存和进程 B 的堆内存互不相干——这就是为什么一个进程崩溃不会影响另一个进程。

## 三、进程的生命周期

一个进程从诞生到消亡，会经历以下状态：

```
        创建              调度器选中          I/O或事件等待
[新建] ────→ [就绪] ────────→ [运行] ──────────→ [阻塞/等待]
  New        Ready          Running            Blocked
              ↑                │                    │
              │    时间片用完    │     I/O完成/事件发生
              └────────────────┘                    │
              ↑                                     │
              └─────────────────────────────────────┘
                                                    
                          正常退出/异常终止
                    [运行] ────────→ [终止]
                    Running          Terminated
```

用排队就医的比喻来理解：

1. **新建 (New)**：你挂号了（进程被创建），但还没进候诊区
2. **就绪 (Ready)**：你在候诊区排队等叫号（进程准备好了，等 CPU 分配时间）
3. **运行 (Running)**：轮到你看病了（CPU 正在执行这个进程的代码）
4. **阻塞 (Blocked)**：医生让你去拍个 CT（进程在等 I/O 操作完成，比如等网络数据返回）
5. **终止 (Terminated)**：看完病走了（进程执行完毕或出错退出）

### 在本项目中的体现

我们的进程爬虫每爬一个学校，就会经历：

```
1. 主进程调用 Command::new("curl") → 创建 curl 子进程 [新建]
2. 操作系统调度 curl 进程执行 → [运行]
3. curl 发出 HTTP 请求后等待网络响应 → [阻塞]
4. 服务器返回数据，curl 继续处理 → [运行]
5. curl 输出结果后退出 → [终止]
6. 主进程收集结果，继续下一个学校
```

## 四、进程间通信（IPC）

既然每个进程有自己独立的内存空间，那它们之间怎么交流信息呢？操作系统提供了几种机制：

### 4.1 常见的 IPC 方式

| 方式 | 比喻 | 特点 | 本项目是否使用 |
|------|------|------|--------------|
| **管道 (Pipe)** | 两个人之间拉一根水管，一头灌水一头接水 | 单向通信，适合父子进程 | **是（stdout 管道）** |
| **消息队列** | 邮局信箱，发信人投递，收信人取件 | 异步，消息可排队 | 否 |
| **共享内存** | 两家公司共用一个会议室白板 | 速度最快，但需要同步 | 否 |
| **信号 (Signal)** | 拍肩膀提醒一下 | 简单通知，不能传数据 | 否 |
| **Socket** | 打电话 | 可跨网络，最通用 | 否 |

### 4.2 本项目中的 IPC

在 `process_crawler.rs` 中，主进程与 curl 子进程之间使用的是**管道（Pipe）**通信：

```rust
let output = Command::new("curl")
    .stdout(Stdio::piped())    // ← 这行代码创建了一个管道！
    .stderr(Stdio::null())     // ← stderr 被丢弃
    .output();                 // ← 等待子进程结束，读取管道中的数据
```

执行流程是这样的：

```
┌──────────┐     管道（pipe）     ┌──────────┐
│  主进程   │ ←────────────────── │ curl子进程 │
│          │  curl的stdout通过   │          │
│ .output()│  管道传回给主进程    │ HTTP下载  │
└──────────┘                     └──────────┘
```

1. 主进程调用 `.stdout(Stdio::piped())` 时，操作系统创建了一个管道
2. curl 子进程的标准输出（stdout）被连接到管道的写入端
3. curl 下载网页内容，写入到 stdout（也就是管道的写入端）
4. 主进程调用 `.output()` 等待 curl 结束，然后从管道的读取端拿到所有数据

这就是为什么我们能在主进程中拿到 curl 下载的 HTML 内容——它们通过管道传递。

## 五、本项目的进程爬虫实现

### 5.1 整体架构

```
┌────────────────────────────────────────────────────────────┐
│                      主进程 (main)                          │
│                                                            │
│  for school in SCHOOLS {                                   │
│      ┌──────────────────────────────────────────┐          │
│      │ 1. 启动 curl 子进程                       │          │
│      │ 2. 等待 curl 完成                         │          │
│      │ 3. 通过管道读取 HTML                      │          │
│      │ 4. HTML → 纯文本                          │          │
│      │ 5. 保存到文件                             │          │
│      │ 6. 记录耗时和结果                         │          │
│      └──────────────────────────────────────────┘          │
│  }                                                         │
│  打印性能统计                                               │
└────────────────────────────────────────────────────────────┘
```

### 5.2 执行时间线

```
时间 ──────────────────────────────────────────────────────→

主进程: [启动curl-北大]──等待──[收到结果][启动curl-清华]──等待──[收到结果][启动curl-浙大]──等待──[收到结果]...
         ↓                                ↓                                ↓
curl-1:  [────── HTTP请求北大 ──────]     |                                |
curl-2:                                  [────── HTTP请求清华 ──────]     |
curl-3:                                                                   [─── HTTP请求浙大 ───]

总耗时 = 所有请求的耗时之和（串行累加）
```

**注意**：虽然我们用的是"进程"模型，但这个实现是**串行**的（一个接一个）。这是一个有意的设计选择——为了展示最基本的进程用法。实际上也可以用 `fork()` 实现多进程并行，但代码会复杂很多。

### 5.3 为什么用 `curl` 命令而不是 HTTP 库？

这是一个刻意的设计决策，目的是**展示进程的特性**：

| 对比 | 调用 `curl` 子进程 | 直接用 `ureq` 库 |
|------|-------------------|-----------------|
| 执行方式 | 创建独立的操作系统进程 | 在当前进程内直接调用函数 |
| 内存隔离 | curl 有独立地址空间 | 共享当前进程的地址空间 |
| 故障影响 | curl 崩溃不影响主程序 | 库函数 panic 会导致整个程序崩溃 |
| 性能开销 | 大（进程创建 + 通信） | 小（只是函数调用） |
| 依赖关系 | 需要系统安装 curl | 编译时内嵌，无外部依赖 |

选择 `curl` 是为了让你真正体会到"进程"是什么——它就是一个**独立运行的程序**，和主进程通过管道通信。

// ↑ 从共享库导入公共工具函数和学校数据

### 6.2 `crawl_one` 函数 — 爬取单个学校

这个函数负责爬取一个学校的网页，是整个程序的核心工作单元。

```rust
fn crawl_one(school: &SchoolInfo, output_dir: &PathBuf) -> (f64, bool, usize) {
//                   ↑ 借用学校信息       ↑ 借用输出目录        ↑ 返回(耗时, 是否成功, 文本长度)
    let start = Instant::now();  // 开始计时
```

#### 创建 curl 子进程

```rust
    let output = Command::new("curl")   // 创建一个新的子进程，运行 curl 命令
        .arg("-s")                      // -s = silent，关闭进度条显示
        .arg("-L")                      // -L = follow redirects，自动跟随 HTTP 重定向
                                        //      很多大学网站会从 http 跳转到 https
        .arg("--max-time").arg("30")    // 最长等待 30 秒，防止某些网站一直无响应
        .arg("-A").arg("Mozilla/5.0 (compatible; Crawler/1.0)")
        //                              ↑ 设置 User-Agent 请求头
        //                              有些服务器会拒绝没有 User-Agent 的请求
        .arg(&school.url)               // 要下载的 URL
        .stdout(Stdio::piped())         // 将 curl 的标准输出通过管道传回给主进程
        .stderr(Stdio::null())          // 丢弃 curl 的错误输出（我们不需要）
        .output();                      // 启动子进程，并等待它完成
        //                              ↑ 注意：这里会阻塞！直到 curl 进程退出
```

**这一行代码做了什么？** 翻译成人话就是：

> "启动一个新的 curl 程序，让它安静地下载这个网页（最多等 30 秒），把下载的内容通过管道传回来给我。"

#### 计算耗时

```rust
    let elapsed_ms = start.elapsed().as_secs_f64() * 1000.0;
    //              ↑ 从 start 到现在经过了多久     ↑ 转成毫秒
```

#### 处理结果

```rust
    match output {
        // 情况一：curl 成功完成且退出码为 0（表示 HTTP 请求成功）
        Ok(output) if output.status.success() => {
            // 将 curl 下载的字节转成字符串
            // from_utf8_lossy: 遇到无效 UTF-8 字节就替换成 "�"，不会崩溃
            let html = String::from_utf8_lossy(&output.stdout).to_string();
            
            // 调用公共库函数，将 HTML 源码转成纯文本
            let text = html_to_text(&html);
            let content_len = text.len();  // 记录文本长度

            // 拼接输出文件路径：例如 "Docs/高校名称和官方网站/北京大学.txt"
            let filepath = output_dir.join(format!("{}.txt", school.name));
            
            // 将纯文本写入文件
            if let Err(error) = fs::write(&filepath, &text) {
                // 写文件失败（比如磁盘满了、没有权限）
                eprintln!("  写入文件失败 {}: {}", school.name, error);
                (elapsed_ms, false, 0)
            } else {
                // 一切顺利！返回成功
                (elapsed_ms, true, content_len)
            }
        }
        // 情况二：curl 失败（网络不通、DNS 解析失败、超时、HTTP 错误等）
        _ => {
            eprintln!("  curl请求失败: {}", school.name);
            (elapsed_ms, false, 0)
        }
    }
}
```

### 6.3 `main` 函数 — 程序入口

#### 初始化

```rust
fn main() {
    let start_total = Instant::now();      // 记录程序总计时起点
    let mem_before = current_rss_kb();     // 记录爬取前的内存占用（RSS）
    //                                      Linux 上读取 /proc/self/status
    //                                      macOS/Windows 上返回 0

    // 构建输出目录的路径
    let output_dir = {
        let mut dir = PathBuf::from(env!("CARGO_MANIFEST_DIR"));
        //                         ↑ 编译时宏，展开为 Cargo.toml 所在目录
        //                           例如 "/home/mofan/OS/OS_itemphase/task1"
        dir.pop();   // 退一级："/home/mofan/OS/OS_itemphase"
        dir.push("Docs");
        dir.push("高校名称和官方网站");
        // 最终路径："/home/mofan/OS/OS_itemphase/Docs/高校名称和官方网站"
        dir
    };
    // 如果目录不存在就递归创建
    fs::create_dir_all(&output_dir).expect("无法创建输出目录");
```

#### 主循环 — 逐个爬取

```rust
    let mut total_success = 0usize;         // 成功计数器
    let mut total_fail = 0usize;            // 失败计数器
    let mut latencies: Vec<f64> = Vec::new(); // 存储每次请求的耗时

    for school in SCHOOLS {
        // SCHOOLS 是一个包含 33 所学校信息的静态数组
        println!("正在爬取: {} ({})", school.name, school.url);

        // ★ 这里是关键：每次循环都创建一个新的 curl 子进程
        // 注意这是串行的——必须等当前学校爬完，才会继续下一个
        let (latency, success, content_len) = crawl_one(school, &output_dir);

        if success {
            total_success += 1;
            println!("  ✓ 成功, 耗时 {:.0}ms, 文本长度 {} 字节", latency, content_len);
        } else {
            total_fail += 1;
            println!("  ✗ 失败, 耗时 {:.0}ms", latency);
        }

        latencies.push(latency);  // 记录这次请求的耗时
    }
```

#### 性能统计输出

```rust
    let total_time = start_total.elapsed();
    let mem_after = current_rss_kb();

    println!("总请求数:       {}", SCHOOLS.len());      // 33
    println!("成功请求数:     {}", total_success);
    println!("失败请求数:     {}", total_fail);
    println!("总耗时:         {:.2} ms", total_time.as_secs_f64() * 1000.0);
    
    // 吞吐率 = 请求数 / 总耗时（秒）
    println!("吞吐率:         {:.2} 请求/秒",
             if total_time.as_secs_f64() > 0.0 {
                 SCHOOLS.len() as f64 / total_time.as_secs_f64()
             } else {
                 0.0
             });

    print_latency_stats(&latencies);         // 打印延迟统计（最小/平均/中位数/P95/最大）
    print_memory_stats(mem_before, mem_after); // 打印内存变化
}
```

## 七、进程模型的优缺点

### 7.1 优点

| 优点 | 说明 | 在本项目中的体现 |
|------|------|----------------|
| **隔离性最强** | 每个进程有独立地址空间，一个崩溃不影响其他 | curl 子进程即使遇到恶意网页崩溃，主进程毫发无损 |
| **编程模型简单** | 不需要考虑线程安全、锁、同步等复杂问题 | 代码最短（仅 123 行），逻辑直白易懂 |
| **利用现有工具** | 可以直接调用系统上的任何命令行工具 | 直接使用 curl 这个成熟的 HTTP 工具 |
| **资源自动回收** | 进程退出后，操作系统自动回收其所有资源 | 每个 curl 进程完成后自动清理 |
| **安全性高** | 进程间不能直接访问对方内存 | 即使 curl 被攻击，也无法读取主进程的数据 |

### 7.2 缺点

| 缺点 | 说明 | 在本项目中的体现 |
|------|------|----------------|
| **创建开销大** | 需要复制页表、分配地址空间（~100μs-数ms） | 33 次创建 curl 进程，累积的进程创建开销不容忽视 |
| **通信成本高** | 必须通过 IPC 机制传递数据 | 通过管道传输整个 HTML 页面的内容 |
| **内存占用大** | 每个进程有独立的内存空间 | 每个 curl 进程约 2-5MB |
| **本实现是串行的** | 当前代码没有实现多进程并行 | 总耗时 = 所有请求耗时之和，吞吐率很低 |
| **依赖外部程序** | 需要系统安装对应的程序 | 如果目标机器没有 curl，程序就无法运行 |

### 7.3 进程模型适合什么？不适合什么？

```
适合 ✓                              不适合 ✗
├── 需要极强隔离性                   ├── 需要高并发的场景
├── 利用已有的命令行工具             ├── 需要频繁通信的场景
├── CPU 密集型且需要多核并行         ├── 对延迟极其敏感的场景
├── 不同任务可能崩溃的场景           └── 资源受限的嵌入式环境
└── 不同任务需要不同权限
```

## 八、适用场景

### 8.1 什么时候应该选择进程模型？

**场景一：需要调用外部工具**

> "我要用 ffmpeg 转码视频，用 ImageMagick 处理图片。"

这些都是独立的可执行程序，你只能通过创建子进程来调用它们。进程模型在这类场景下是**唯一选择**。

**场景二：需要极强的故障隔离**

> "我的爬虫要爬取上万个网站，有些网站可能包含恶意代码。"

用进程模型，即使某个子进程被恶意代码攻击并崩溃，也不会影响主程序和其他子进程。这在安全敏感的场景中非常重要。

**场景三：CPU 密集型的并行计算**

> "我要对大量数据做复杂的数学运算。"

在一些语言（如 Python）中，由于语言设计的限制，线程无法真正并行。这时候多进程是实现真正并行计算的方式。（注意：Rust 没有这个限制，多线程也可以真正并行）

**场景四：需要不同权限或资源限制**

> "某些任务需要 root 权限，但主程序不应该拥有。"

可以以不同的用户身份启动子进程，实现权限隔离。

### 8.2 在本项目中为什么用进程？

本项目使用进程模型**并非因为它最高效**（实际上它在三种方案中性能最差），而是为了：

1. **对比教学**：让你看到进程模型的特点和局限性
2. **展示 IPC**：通过管道通信演示进程间如何交换数据
3. **展示隔离性**：curl 崩溃不影响主程序

## 九、一句话记住

> **进程就像独立的公司——每个都有自己的办公室（内存空间），安全隔离但沟通成本高。适合需要强隔离或调用外部工具的场景，但不适合高并发。**
