## 一、什么是线程？

### 1.1 用生活比喻理解

在[进程爬虫详解](进程爬虫详解.md)中，我们把进程比作独立的公司。现在来看**线程**：

想象一家公司（进程）里有多个员工（线程）。这些员工：
- **共享同一间办公室**（内存空间）——文件柜、打印机、白板都是大家共用的
- **各自有自己的桌子**（栈空间）——每个人的私人物品放在自己桌上
- **可以直接交流**——喊一嗓子同事就能听到，不需要打电话或发快递
- **但需要排队使用公共资源**——打印机同时只能一个人用，需要轮流

这就是线程的核心特点：**同一个进程内的多个执行流，共享内存但各有独立的执行栈。**

### 1.2 技术定义

**线程（Thread）** 是 CPU 调度的基本单位，是进程内的一个独立执行流。

关键要素：
- **每个线程有自己的**：程序计数器（PC，记录当前执行到哪一行）、栈（存放局部变量）、寄存器状态
- **线程之间共享**：进程的地址空间（堆内存、全局变量、代码段）、文件描述符、信号处理器

一个进程至少有一个线程（主线程）。当你运行 `cargo run --bin thread_crawler` 时：
1. 操作系统创建一个进程
2. 进程中自动有一个主线程开始执行 `main()` 函数
3. 主线程通过 `thread::spawn()` 创建 33 个子线程
4. 34 个线程（1 个主线程 + 33 个子线程）并发执行

### 1.3 线程 vs 进程 — 一图看懂

```
进程模型（独立的公司）：

┌────────────────┐    ┌────────────────┐    ┌────────────────┐
│ 进程 A         │    │ 进程 B         │    │ 进程 C         │
│ ┌────────────┐ │    │ ┌────────────┐ │    │ ┌────────────┐ │
│ │ 代码+数据  │ │    │ │ 代码+数据  │ │    │ │ 代码+数据  │ │
│ │ 堆内存     │ │    │ │ 堆内存     │ │    │ │ 堆内存     │ │
│ │ 栈         │ │    │ │ 栈         │ │    │ │ 栈         │ │
│ └────────────┘ │    │ └────────────┘ │    │ └────────────┘ │
│  完全独立       │    │  完全独立      │    │  完全独立       │
└────────────────┘    └────────────────┘    └────────────────┘

线程模型（同一家公司的多个员工）：

┌───────────────────────────────────────────────────┐
│ 进程（一家公司）                                    │
│ ┌─────────────────────────────────────┐            │
│ │ 共享区域：代码段 + 堆内存 + 全局变量  │            │
│ └─────────────────────────────────────┘            │
│                                                    │
│ ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│ │ 线程1    │  │ 线程2    │  │ 线程3    │ ...       │
│ │ 自己的栈  │  │ 自己的栈  │  │ 自己的栈  │          │
│ │ 自己的PC  │  │ 自己的PC  │  │ 自己的PC  │          │
│ └──────────┘  └──────────┘  └──────────┘          │
└───────────────────────────────────────────────────┘
```

## 二、线程与进程的关系

### 2.1 包含关系

```
操作系统
  └── 进程 A
  │     ├── 主线程
  │     ├── 子线程 1
  │     ├── 子线程 2
  │     └── ...
  └── 进程 B
        ├── 主线程
        └── ...
```

- 一个操作系统可以运行多个进程
- 每个进程可以包含多个线程
- 线程不能脱离进程独立存在
- 当进程终止时，进程内的所有线程也会被终止

### 2.2 核心区别对照表

| 对比维度 | 进程 | 线程 |
|---------|------|------|
| **内存空间** | 每个进程独立（互相看不到） | 同进程内的线程共享（互相能看到） |
| **创建成本** | 高（~100μs-数ms，需要复制页表、分配地址空间） | 低（~1-10μs，只需分配栈空间） |
| **切换成本** | 高（需要切换地址空间、刷新 TLB 缓存） | 较低（共享地址空间，无需刷新 TLB） |
| **通信方式** | 需要 IPC（管道、消息队列等） | 直接读写共享内存 |
| **安全隔离** | 强（一个崩溃不影响其他） | 弱（一个崩溃整个进程死亡） |
| **数据竞争** | 不存在（各自独立） | 可能存在（需要同步机制保护） |
| **典型用量** | 数百个 | 数千个 |

### 2.3 为什么需要线程？

用一个例子说明。假设你要同时下载 33 个网页：

**只用进程（串行）**：
- 下载网页1...等待 → 下载网页2...等待 → ... → 下载网页33...等待
- 总耗时 = 所有等待时间之和

**用线程（并发）**：
- 线程1下载网页1，同时线程2下载网页2，同时线程3下载网页3...
- 总耗时 ≈ 最慢的那个网页的时间

为什么不用多个进程来并行？当然可以，但线程更轻量、创建更快、通信更方便。在同一个程序内做并发，线程是比进程更自然的选择。

## 三、线程共享了什么，独占了什么

这是理解线程的关键，也是理解"线程安全"问题的基础。

### 3.1 共享的资源（所有线程都能访问）

```
┌─────────────────────────────────────────┐
│              进程的共享资源               │
│                                         │
│  ┌─────────────┐  ┌─────────────┐      │
│  │  代码段      │  │  全局/静态   │      │
│  │（程序指令）  │  │   变量       │      │
│  └─────────────┘  └─────────────┘      │
│                                         │
│  ┌─────────────┐  ┌─────────────┐      │
│  │  堆内存      │  │  文件描述符  │      │
│  │（Vec/String）│  │  （打开的文件）│     │
│  └─────────────┘  └─────────────┘      │
│                                         │
│  ┌──────────────────────────────┐       │
│  │  进程 ID、环境变量、信号处理器  │       │
│  └──────────────────────────────┘       │
└─────────────────────────────────────────┘
```

### 3.2 每个线程独占的资源

```
┌──────────────────┐
│     线程私有       │
│                  │
│  ┌────────────┐  │
│  │ 栈 (Stack) │  │ ← 局部变量、函数调用链
│  │  默认2-8MB  │  │   每个线程一份独立的栈
│  └────────────┘  │
│                  │
│  ┌────────────┐  │
│  │ 寄存器状态  │  │ ← 程序计数器(PC)、栈指针(SP)等
│  │  (Context)  │  │   线程切换时需要保存/恢复
│  └────────────┘  │
│                  │
│  ┌────────────┐  │
│  │ 线程 ID    │  │ ← 操作系统分配的唯一标识
│  └────────────┘  │
└──────────────────┘
```

### 3.3 为什么这很重要？

因为"共享"意味着**可能同时被多个线程修改**，这就会产生**数据竞争**问题。

举个生活中的例子：假设办公室有一个共享的咖啡计数器（记录今天泡了几杯咖啡），两个员工同时去修改它：

```
原始值：counter = 5

员工A（线程A）的操作：          员工B（线程B）的操作：
1. 读取 counter = 5            1. 读取 counter = 5
2. 计算 5 + 1 = 6              2. 计算 5 + 1 = 6
3. 写回 counter = 6            3. 写回 counter = 6

预期结果：counter = 7（两杯新咖啡）
实际结果：counter = 6（丢失了一次计数！）
```

这就是经典的**数据竞争（Data Race）**。为了避免这种问题，我们需要**同步原语**。

## 四、线程安全与同步原语

### 4.1 什么是同步原语？

同步原语就是保证多个线程安全访问共享资源的工具。就像办公室里的"门锁"和"排队规则"：

#### 互斥锁 (Mutex)

```
比喻：公司只有一个厕所，同时只能一个人进去，进去要锁门。

┌──────┐
│ Mutex │  ← 任何时刻只有一个线程能"锁住"它
└──────┘
   │
   ├── 线程A: lock() → 使用数据 → unlock()
   │                        ↑ 这段时间内其他线程必须等待
   ├── 线程B: lock() → [等待A释放] → 使用数据 → unlock()
   └── 线程C: lock() → [等待B释放] → 使用数据 → unlock()
```

Rust 代码示例：
```rust
use std::sync::Mutex;
let counter = Mutex::new(0);        // 创建一个被锁保护的计数器
let mut num = counter.lock().unwrap(); // 获取锁
*num += 1;                           // 安全地修改数据
// 锁在 num 离开作用域时自动释放
```

#### 信道/通道 (Channel)

```
比喻：公司内部的传送带——一头放东西（send），另一头取东西（recv）。

发送端(Sender)                  接收端(Receiver)
  线程1 ──send──→ ┌─────────┐ ──recv──→ 主线程
  线程2 ──send──→ │ 传送带   │
  线程3 ──send──→ └─────────┘
                   ↑ 多个发送者，一个接收者 (mpsc)
```

这是本项目**线程爬虫实际使用的同步原语**！

#### 信号量 (Semaphore)

```
比喻：停车场有20个车位，有车出去才能有新车进来。

容量=20: ████████████████████ (20个许可证)
             ↑
         同时最多20个线程可以进入
```

这是本项目**协程爬虫使用的原语**（将在[协程爬虫详解](协程爬虫详解.md)中详细介绍）。

### 4.2 Rust 如何保证线程安全？（Rust 特有，可跳过）

> 本节涉及 Rust 语言的特性。如果你只想了解线程的通用概念，可以跳到[第五节](#五本项目的线程爬虫实现)。

Rust 通过编译器（类型系统）在**编译时**就防止了数据竞争，这是 Rust 最独特的优势之一。

核心规则由两个 trait 控制：

| Trait | 含义 | 比喻 |
|-------|------|------|
| `Send` | 数据可以安全地从一个线程转移到另一个线程 | 这个东西可以通过快递寄给同事 |
| `Sync` | 数据可以安全地被多个线程同时引用 | 这个东西可以放在公告栏让大家同时看 |

如果你写的代码试图把一个非 `Send` 的值传给另一个线程，Rust 编译器会**直接报错**，程序编译不过去。这意味着很多线程安全 Bug 在 C/C++/Java 中需要运行时才能发现（甚至难以重现），在 Rust 中编译阶段就被拦住了。

### 4.3 本项目中的线程安全设计（Rust 特有，可跳过）

```rust
// ① SCHOOLS 是 &'static [SchoolInfo]
//    'static 生命周期 → 数据在程序整个运行期间都存在
//    &'static 引用 → 实现了 Send + Sync → 可以安全传给任何线程

// ② mpsc::channel() 的 Sender 实现了 Send
//    .clone() 后每个线程拥有自己的 Sender 副本
//    线程通过各自的 Sender 发送结果，不存在竞争

// ③ PathBuf 实现了 Send + Clone
//    .clone() 后每个线程拥有独立副本，不共享可变状态
```

关键设计决策：**本项目的线程爬虫完全没有使用 Mutex！** 因为它巧妙地避免了共享可变状态——每个线程独立工作，结果通过 Channel 传回，不需要加锁。

## 五、本项目的线程爬虫实现

### 5.1 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│                        主线程 (main)                         │
│                                                              │
│  1. 创建 Channel（传送带）                                    │
│  2. 为每所学校创建一个线程                                    │
│  3. 等待所有线程完成                                          │
│  4. 从 Channel 收集所有结果                                   │
│  5. 打印统计信息                                              │
│                                                              │
│  ┌────────┐  ┌────────┐  ┌────────┐       ┌────────┐       │
│  │ 线程1  │  │ 线程2  │  │ 线程3  │  ...  │ 线程33 │       │
│  │ 爬北大  │  │ 爬清华 │  │ 爬人大  │       │ 爬兰大  │       │
│  │        │  │        │  │        │       │        │       │
│  │ ureq   │  │ ureq   │  │ ureq   │       │ ureq   │       │
│  │ HTTP   │  │ HTTP   │  │ HTTP   │       │ HTTP   │       │
│  └───┬────┘  └───┬────┘  └───┬────┘       └───┬────┘       │
│      │           │           │                 │            │
│      └───────────┴───────────┴───────┬─────────┘            │
│                                      ↓                      │
│                              ┌──────────────┐               │
│                              │   Channel    │               │
│                              │  (结果传送带) │               │
│                              └──────┬───────┘               │
│                                     ↓                       │
│                              主线程收集结果                   │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 执行时间线

```
时间 ────────────────────────────────────────────────────────→

主线程:  [创建线程1-33] ──── [等待 join] ──── [收集结果] [打印统计]
              │
              ├─ 线程1:  [── HTTP请求北大 (200ms) ──]──send──→ Channel
              ├─ 线程2:  [──── HTTP请求清华 (300ms) ────]──send──→
              ├─ 线程3:  [── HTTP请求人大 (150ms) ─]──send──→
              ├─ ...
              └─ 线程33: [──── HTTP请求兰大 (400ms) ────────]──send──→

              ↑ 所有线程同时并发执行！

总耗时 ≈ max(所有请求耗时) + 线程创建/调度开销
       ≈ 400ms + 一点点额外开销
```

对比进程爬虫的串行执行（总耗时 = 所有请求耗时之和），线程爬虫的优势一目了然。

### 5.3 Channel 的工作原理详解

Channel（信道）是本项目线程间通信的核心。让我们详细理解它。

```
mpsc = Multi-Producer, Single-Consumer
       多个生产者       一个消费者

创建：let (sender, receiver) = mpsc::channel();

      sender（发送端）                receiver（接收端）
      可以 .clone() 复制              只能有一个
      每个线程拿一份                  主线程持有

数据流向：

  线程1的sender ──send(结果1)──→ ┌──────────┐
  线程2的sender ──send(结果2)──→ │  内部队列  │ ──recv()──→ 主线程取出结果
  线程3的sender ──send(结果3)──→ │  (FIFO)   │
  ...                           └──────────┘
  线程33的sender ──send(结果33)→

发送顺序不确定：哪个线程先完成 HTTP 请求，就先 send
接收顺序：先进先出（FIFO），先发送的先被取出
```

**为什么选 Channel 而不是 Mutex？**

| 方式 | 实现方式 | 复杂度 |
|------|---------|--------|
| Mutex | 创建一个 `Arc<Mutex<Vec<Result>>>` 共享给所有线程 | 需要考虑加锁/解锁时机 |
| Channel | 每个线程独立 send，主线程统一 recv | 线程间完全解耦，代码更清晰 |

在 Rust 社区有一句名言：**"不要通过共享内存来通信，而要通过通信来共享内存"**。Channel 正是这一理念的体现。

```rust
        dir.pop();
        dir.push("Docs");
        dir.push("高校名称和官方网站");
        dir
    };
    fs::create_dir_all(&output_dir).expect("无法创建输出目录");
```

#### 创建 Channel 和线程

这是线程爬虫最核心的部分：

```rust
    // 创建通道：sender 用于发送结果，receiver 用于接收结果
    let (sender, receiver) = mpsc::channel();
    let mut handles = Vec::new();  // 存储所有线程的句柄

    for school in SCHOOLS {
        let sender = sender.clone();
        //  ↑ 为什么要 clone？
        //  因为 sender 要 move 进线程闭包（每个线程拥有自己的 sender）
        //  mpsc::channel 允许多个 sender（多生产者），所以可以 clone
        //  clone 的代价很小——只是增加内部引用计数

        let dir = output_dir.clone();
        //  ↑ PathBuf 也需要 clone
        //  因为每个线程需要拥有自己的路径副本
        //  如果用 &output_dir 借用，编译器会报错：
        //  "borrowed value does not live long enough"
        //  因为无法保证 output_dir 比线程活得更久

        let handle = thread::spawn(move || {
            //                     ↑ move 关键字！
            //  把 sender、dir、school 的所有权转移到线程闭包中
            //  这是 Rust 确保线程安全的关键机制：
            //  - 要么转移所有权（move），保证只有一个线程拥有数据
            //  - 要么使用 Arc（原子引用计数）共享不可变数据
            //  - 要么使用 Arc<Mutex> 共享可变数据
            
            let result = crawl_one_task(school, dir);
            // ↑ 在子线程中执行爬取任务

            sender.send(result).ok();
            // ↑ 将结果通过通道发送给主线程
            // .ok() 忽略发送失败（如果主线程已经退出，就不管了）
        });

        handles.push(handle);
        // ↑ 保存线程句柄，后续用于等待线程完成
    }
```

让我们详细解释 `move` 关键字，这是初学者最容易困惑的地方：

```
不用 move 的情况（不工作，编译器会报错）：

    主线程栈                     子线程
    ┌──────────┐                ┌──────────┐
    │ sender   │ ←── 借用 ────── │ &sender  │ ← 子线程借用了主线程的 sender
    │ dir      │ ←── 借用 ────── │ &dir     │ ← 但主线程可能先退出！
    └──────────┘                └──────────┘
    ↑ 如果主线程先结束，sender 被释放，子线程的引用就悬空了！危险！


用 move 的情况（安全）：

    主线程栈                     子线程
    ┌──────────┐                ┌──────────┐
    │ (sender  │ ──转移──→       │ sender   │ ← 子线程拥有 sender
    │  已移走)  │                │ dir      │ ← 子线程拥有 dir
    └──────────┘                └──────────┘
    ↑ 主线程不再拥有 sender       ↑ 子线程完全拥有数据，不依赖主线程
```

#### 等待所有线程完成

```rust
    println!("已启动 {} 个线程, 等待完成...", handles.len());  // 33
    
    for handle in handles {
        handle.join().ok();
        // ↑ join() 的含义：阻塞当前线程（主线程），
        //   直到这个子线程执行完毕
        //
        //   .ok() 忽略子线程中的 panic
        //   如果某个线程崩溃了，主线程不会跟着崩溃
    }
    
    drop(sender);
    // ↑ 显式关闭主线程持有的 sender
    //   这很重要！因为 mpsc::channel 有一个规则：
    //   只有当所有 sender 都被释放后，
    //   receiver 才知道不会再有新数据过来
    //
    //   如果不 drop(sender)，receiver 会一直等待
    //   可能导致程序永远不结束
    //
    //   此时每个子线程的 sender 在线程结束时已自动释放
    //   主线程的这个 sender 是最后一个，drop 后 channel 彻底关闭
```

**为什么需要 `drop(sender)`？** 让我画一个图：

```
创建 channel:  sender（原始） + receiver
clone:         sender（原始）+ sender_clone_1 + sender_clone_2 + ... + receiver

线程1结束 → sender_clone_1 释放
线程2结束 → sender_clone_2 释放
...
线程33结束 → sender_clone_33 释放
drop(sender) → 原始 sender 释放

此时所有 sender 都释放了 → receiver.try_recv() 返回 Err → 循环结束
```

#### 收集结果

```rust
    let mut total_success = 0usize;
    let mut total_fail = 0usize;
    let mut latencies: Vec<f64> = Vec::new();

    while let Ok((name, latency, success, content_len)) = receiver.try_recv() {
        //                                                ↑ try_recv 是非阻塞的
        //   如果通道中有数据 → 返回 Ok(数据)
        //   如果通道为空且还有 sender → 返回 Err(TryRecvError::Empty)
        //   如果通道为空且所有 sender 都关闭 → 返回 Err(TryRecvError::Disconnected)
        //
        //   因为我们已经 join 了所有线程且 drop 了 sender
        //   所以此处 Err 意味着所有数据都已取出
        
        if success {
            total_success += 1;
            println!("✓ {} : 耗时 {:.0}ms, 文本长度 {} 字节", name, latency, content_len);
        } else {
            total_fail += 1;
            println!("✗ {} : 耗时 {:.0}ms", name, latency);
        }
        latencies.push(latency);
    }
```

## 七、线程模型的优缺点

### 7.1 优点

| 优点 | 说明 | 在本项目中的体现 |
|------|------|----------------|
| **真正的并发** | 多个线程可以在多个 CPU 核心上同时运行 | 33 个线程同时发起 HTTP 请求，总耗时大幅缩短 |
| **创建成本低** | 比进程轻量得多（~1-10μs vs ~100μs+） | 33 个线程的创建开销总共只有毫秒级 |
| **通信简单** | 共享地址空间，可通过 Channel 或共享变量通信 | 用 mpsc::channel 优雅地传递结果 |
| **编程模型直观** | 每个线程执行的代码和普通函数一样 | `crawl_one_task` 就是一个普通函数 |
| **无需外部依赖** | 使用标准库即可 | 只需 `std::thread` 和 `std::sync` |

### 7.2 缺点

| 缺点 | 说明 | 在本项目中的体现 |
|------|------|----------------|
| **内存开销不低** | 每个线程默认栈空间 2-8MB | 33 线程可能占用 66-264MB 栈空间 |
| **隔离性弱** | 一个线程 panic 可能导致整个进程崩溃 | 虽然 `.join().ok()` 能捕获 panic，但共享内存可能被破坏 |
| **线程切换有成本** | 内核态线程切换约需数微秒 | 33 个线程在有限 CPU 核心上切换产生额外开销 |
| **数量有上限** | 操作系统对线程数有限制 | 如果要爬 10000 个网站，创建 10000 个线程就不现实了 |
| **需要考虑线程安全** | 共享数据必须用同步原语保护 | 虽然本项目通过设计避免了，但实际项目中这是常见痛点 |

### 7.3 线程数量的限制

```
33 个线程：完全没问题
333 个线程：大多数系统可以承受
3,333 个线程：开始吃力（内存 6-26GB 的栈空间）
33,333 个线程：大多数系统会 OOM（内存溢出）或报错

这就是为什么需要协程——协程可以轻松支持数万甚至数十万的并发任务
```

## 八、适用场景

### 8.1 什么时候应该选择线程模型？

**场景一：中等规模的并发 I/O 任务**

> "我要同时下载 10-100 个文件。"

线程数量不多，创建和管理的开销可以接受。每个线程阻塞在 I/O 等待上不会浪费太多资源（操作系统会自动调度）。

**场景二：已有同步阻塞代码，想加并行**

> "我的 HTTP 库是同步的（比如 ureq），我不想改成异步的。"

这正是本项目的情况！ureq 是一个同步 HTTP 库，调用 `.call()` 会阻塞当前线程。用线程模型可以直接把同步代码"扔到"各个线程中运行。

**场景三：CPU 密集型并行计算**

> "我要对大量图片做缩放处理。"

每个线程处理一张图片，可以充分利用多核 CPU 的计算能力。这种场景下线程是比协程更好的选择，因为协程在 CPU 密集型任务中没有优势（协程的优势在 I/O 等待时让出执行权）。

**场景四：需要简单直观的代码**

> "团队成员不熟悉 async/await，需要快速上线。"

线程的编程模型最接近传统的顺序编程——每个线程中的代码从上往下执行，不需要 `.await`、不需要异步运行时。

### 8.2 在本项目中为什么用线程？

1. **展示并发能力**：对比进程的串行执行，线程实现了真正的并发
2. **展示线程通信**：mpsc::channel 是 Rust 最经典的线程间通信方式
3. **代码复杂度适中**：比进程稍复杂（需要理解 move、clone、join），比协程简单（不需要 async/await）
4. **直接使用同步库**：ureq 是同步的，线程模型可以直接使用，不需要 spawn_blocking 这样的包装
