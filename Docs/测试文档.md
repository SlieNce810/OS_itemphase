## 二、测试工具

无需额外安装测试工具。整个项目为纯 Rust 实现，所有性能指标（延迟、吞吐率、内存）由程序本身在运行时采集并输出。

- **计时**: `std::time::Instant` — 纳秒级精度
- **内存**: `/proc/self/status` 中的 `VmRSS` 字段 — 实际物理内存占用
- **HTTP客户端**: 
  - 进程爬虫使用系统 `curl` 命令
  - 线程爬虫和协程爬虫使用 `ureq` crate

## 三、构建与运行

### 3.1 构建（编译）

```bash
# 进入项目目录
cd /home/mofan/OS/OS_itemphase/task1

# 编译所有三个程序（Release 模式以获得最佳性能）
cargo build --release
```

编译产物位置：
```
target/release/process_crawler   # 进程爬虫
target/release/thread_crawler    # 线程爬虫
target/release/async_crawler     # 协程爬虫
```

### 3.2 单独运行

```bash
# 运行进程爬虫
cargo run --release --bin process_crawler

# 运行线程爬虫
cargo run --release --bin thread_crawler

# 运行协程爬虫
cargo run --release --bin async_crawler
```

### 3.3 一键运行全部并保存输出

```bash
# 清空之前的输出文件
rm -f ../Docs/*.txt

# 依次运行三个爬虫，保存日志
cargo run --release --bin process_crawler 2>&1 | tee ../Docs/process_output.log
cargo run --release --bin thread_crawler 2>&1 | tee ../Docs/thread_output.log
cargo run --release --bin async_crawler 2>&1 | tee ../Docs/async_output.log
```

## 七、结果分析与直观比较

### 7.1 延迟对比

进程爬虫因**串行执行**，总耗时 = Σ(所有请求耗时)，远远大于线程和协程方案。

线程和协程方案实现了**并发执行**，总耗时 ≈ max(单次请求耗时)。在线程和协程之间，协程通常略快，因为：

1. **协程切换开销更小**：协程是用户态状态机切换（~几纳秒），线程需要内核态上下文切换（~几微秒）
2. **内存局部性更好**：协程复用少量线程，缓存命中率更高
3. **调度更灵活**：tokio 的工作窃取调度器能更好地平衡负载

### 7.2 吞吐率对比

- 进程爬虫：串行决定了吞吐率最低
- 线程爬虫：33个线程同时发出请求，吞吐率高，但受线程创建开销影响
- 协程爬虫：同样的并发度，但创建/销毁开销更小，吞吐率最高

### 7.3 内存对比

- 进程爬虫：33个curl进程，每个约2-5MB，总内存增量最大
- 线程爬虫：33个线程，每个默认栈8MB，如果栈是懒分配的可能实际少些
- 协程爬虫：协程本身内存占用极小（数百字节），内存增量最小

### 7.4 代码复杂度

| 维度       | 进程                    | 线程                   | 协程                      |
|-----------|------------------------|------------------------|--------------------------|
| 并发控制    | 天然隔离，最简单         | 需要 channel/Arc/Mutex  | 需要 async runtime/Semaphore |
| 错误处理    | 进程级隔离              | std::thread::Result    | JoinHandle 需 .await       |
| 编程模型    | 同步，无特殊语法         | 同步，无特殊语法         | async/await，函数染色问题   |
| 调试难度    | 简单（每个进程独立）      | 中等（多线程竞态问题）    | 中等（async 栈回溯不直观）   |
